# OS · 基于 eBPF 的 openEuler 系统异常观测与根因定位工具

> 全国大学生计算机系统能力大赛 · 操作系统设计赛（华东区域赛）· 操作系统应用开发赛道参赛项目
> 运行环境：openEuler 24.03 LTS（内核 6.6） · 工作代号：osmedic

一个轻量级、高实时性的系统异常观测与诊断工具：用 **eBPF** 在内核侧实时采集 5 类典型异常的现场数据，用**规则引擎**推断疑似根因并组装证据链，输出**结构化 JSON 诊断报告**，并由 **LLM** 生成人类可读的诊断建议。

## 为什么做这个

传统的日志分析和静态监控手段，难以应对高频、瞬时的系统性能异常——等人工登录排查时，现场早就没了。eBPF 以低侵入、低开销的特性成为内核级观测的关键技术：不改内核源码、不写内核模块、生产环境可常开。本项目用它构建一个**可运行、可解释、可复现**的诊断工具。

## 核心功能（对齐赛题要求）

观测并诊断 **5 类典型异常场景**：

| # | 场景 | 回答的问题 |
|---|---|---|
| 1 | 高频 / 高耗时系统调用热点 | 谁在疯狂调用 syscall？调用谁？ |
| 2 | CPU 异常占用 / 调度延迟 | 谁在持续吃满 CPU？谁在等待调度？ |
| 3 | I/O 延迟抖动 / 阻塞等待 | 热点文件/设备/队列拥堵在哪？ |
| 4 | 内存抖动 / OOM 风险 | 大块内存申请、回收压力、缺页激增来自谁？ |
| 5 | 锁竞争性能退化 | 热点锁在哪？哪些线程在排队？ |

**诊断输出契约**（结构化 JSON，对齐评分细则）：异常类型、关联对象、关键指标、异常时间窗口、疑似根因、证据链、建议性结论。

**架构**：规则引擎保证诊断准确性（确定性判断），LLM 只做解释层（把结构化证据翻译成人话）——AI 不参与判断，只参与表达。

```
eBPF 探针层 ──► 采集代理 ──► 聚合与特征层 ──► 规则诊断引擎 ──► JSON 诊断报告
（内核态）        （用户态）    （系统画像/基线）    （根因+证据链）        │
                                                                          ▼
                                                                  LLM 可读报告（差异化）
```

## 环境要求

- openEuler 24.03 LTS（内核 6.6，原生支持 eBPF）
- 工具链：`dnf install -y bpftrace bcc-tools libbpf-devel clang llvm make git stress-ng fio sysstat kernel-devel`

快速验证（一条命令即可看到内核里的实时事件，eBPF 版 Hello World）：

```bash
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'
```
