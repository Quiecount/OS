# 阶段1 探针基础实现与验收

## 1 交付结论

阶段1完成两支基于 libbpf CO-RE 的 eBPF 探针，并提供统一构建、JSON Lines 落盘和端到端验收流程：

1. `execsnoop`：挂载 `syscalls:sys_enter_execve`，通过 ring buffer 把进程启动事件传到用户态。
2. `biolatency`：挂载 `block_rq_issue` 与 `block_rq_complete` raw tracepoint，以 request 指针关联开始和完成事件，按块设备聚合延迟直方图。
3. 两个用户态加载器均可限时运行、响应 `SIGINT/SIGTERM`，并把机器可解析的 JSONL 写到标准输出或指定文件。
4. `scripts/stage1-smoke.sh` 自动执行构建、故障负载、JSON 解析与字段断言，最终输出 `STAGE1_SMOKE_OK`。

## 2 目录与职责

```text
src/common/osmedic.h          内核态和用户态共享的数据结构
src/probes/execsnoop.bpf.c    execve ringbuf 探针
src/probes/biolatency.bpf.c   块 I/O 延迟直方图探针
src/loader/execsnoop.c        exec 事件 JSONL 加载器
src/loader/biolatency.c       I/O 直方图 JSONL 加载器
scripts/stage1-smoke.sh       阶段1端到端验收
Makefile                      vmlinux.h、BPF 对象、skeleton、加载器构建
```

## 3 构建方式

目标环境为 openEuler 24.03 LTS，要求 `/sys/kernel/btf/vmlinux` 存在，并安装 `clang`、`bpftool`、`libbpf-devel`、`elfutils-libelf-devel`、`zlib-devel`、`make` 与 `gcc`。

```bash
make
make check
```

构建会从当前运行内核的 BTF 生成 `build/vmlinux.h`，再生成 BPF skeleton。`Makefile` 根据 `uname -m` 自动选择 x86、arm64 或 riscv 的目标宏。

## 4 使用方式

### 4.1 execve 追踪

```bash
sudo ./build/execsnoop --duration 10 --output output/exec.jsonl
```

单行输出示例：

```json
{"schema_version":1,"event":"process_exec","timestamp":"2026-11-17T03:20:01.125Z","ktime_ns":123456789,"pid":1234,"tid":1234,"uid":1000,"comm":"bash","filename":"/usr/bin/ls"}
```

### 4.2 块 I/O 延迟直方图

```bash
sudo ./build/biolatency --interval 5 --duration 30 --output output/io.jsonl
```

每个输出窗口按设备生成一行 JSON，其中 `buckets` 是 26 个以微秒为单位的 2 次幂上界桶。最后一个桶同时承接超过其上界的延迟样本。

## 5 一键验收

```bash
sudo bash scripts/stage1-smoke.sh
```

脚本会执行以下检查：

1. `make check` 成功，两个加载器均为可执行文件。
2. 启动 `execsnoop` 后执行 `true` 和 `uname`，JSONL 至少捕获一条 `process_exec`。
3. 启动 `biolatency` 后用 `dd` 产生同步写 I/O，JSONL 至少生成一个设备直方图。
4. Python 逐行解析 JSON，验证事件类型、必需字段、样本数及 26 个桶。

## 6 Verifier 学习与排错记录

阶段1要求成员能够读懂 Verifier 拒绝原因。建议在个人分支进行以下练习，不把故意错误合入主分支：

1. 把 BPF 栈上局部数组扩大到 600 字节，观察 `combined stack size ... exceeds 512 bytes`。
2. 去掉 map 查找结果的空指针判断，观察 `R0 invalid mem access 'map_value_or_null'` 一类错误。
3. 使用来自 tracepoint 的不可信索引直接访问数组，观察越界相关拒绝信息，再通过边界判断修复。

调试时可临时设置 `LIBBPF_LOG_LEVEL=debug`，并保留完整加载日志作为阶段过程性资料。复杂格式化、时间转换和 JSON 序列化均放在用户态，降低 Verifier 复杂度。

## 7 当前边界

- I/O 探针按 request 指针做关联，可避免仅用扇区号关联造成的并发碰撞；若驱动产生未配对事件，`starts` map 的容量上限为 16384。
- 阶段1只输出原始事件和时间窗口直方图，不在内核态做 P99 或根因判断；分位数与诊断规则属于后续聚合层。
- 加载 tracing 类 BPF 程序通常需要 root，或为程序配置 `CAP_BPF`、`CAP_PERFMON` 等最小能力。验收脚本默认使用 root。
- 当前已针对 openEuler 24.03 LTS 内核 6.6 的 BTF 和 tracepoint 原型构建；跨内核验证在后续多平台阶段补充。

## 8 验证记录

2026-11-17 在 openEuler 24.03 LTS（内核 `6.6.0-145.0.13.139.oe2403.x86_64`）执行：

- `make clean && make check`：通过，clang 17 和 libbpf 1.2.2 下零警告。
- `llvm-objdump -h`：确认 exec 探针包含 `tracepoint/syscalls/sys_enter_execve`、`.maps`、`.BTF` 与 `.BTF.ext`；I/O 探针包含 `raw_tp/block_rq_issue`、`raw_tp/block_rq_complete`、`.maps`、`.BTF` 与 `.BTF.ext`。
- 两个加载器 `--help`：通过。
- 普通用户加载测试：按预期被内核以 `Operation not permitted` 拒绝，证明端到端验证必须使用 root 或最小 capabilities。
- root 端到端 smoke test：通过。捕获 2 条 exec 事件和 1 条 `sda` 设备直方图；直方图包含 67 个 I/O 样本，脚本输出 `STAGE1_SMOKE_OK`。
- JSONL 样本核对：exec 事件包含时间戳、PID/TID、UID、进程名和可执行文件路径；I/O 事件包含设备号、2 秒窗口、样本总数和 26 个延迟桶。
