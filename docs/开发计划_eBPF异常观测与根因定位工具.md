> 制定日期：2026-11-06 · 适用团队：零基础、无专用硬件

## 一、我们要做什么（一页说清）

**一句话**：做一个跑在 openEuler 上的 eBPF 工具，实时观测 5 类系统异常（CPU / IO / 内存 / 锁 / 系统调用热点），自动诊断根因，输出结构化 JSON 报告 + LLM 可读报告。

```
 eBPF 探针（内核态）──► 聚合层（用户态）──► 规则诊断引擎 ──► JSON 结构化报告
  5 类异常场景采集        统计/基线对比        疑似根因+证据链      │
                                                                   ▼
                                                        LLM 可读诊断报告（差异化亮点）
```

**设计原则（对应评分细则）**：

- **准确性靠规则引擎**（确定性逻辑，识别/定位不瞎猜）→ 保 30 分诊断准确性
- **可读性靠 LLM**（只做解释层，喂结构化证据，不做判断层）→ 差异化创新分
- **每个场景、每层都能独立演示**——进度永不陷入"全写完才能看"的险境

**评分项 → 我们的得分策略**：

| 评分项 | 分值 | 拿分策略 |
|---|---|---|
| 功能完成度 | 40 | 5 场景全覆盖（15）+ JSON 七字段完整输出（15）+ 双内核版本 & 双架构适配（10） |
| 诊断准确性 | 30 | 用故障注入脚本制造"已知根因"的异常 → 建自动判分测试集，误报/漏报率可控 |
| 性能开销 | 15 | 开销评测四小项（CPU/内存/时延/吞吐）做成对照表，开发期持续记录 |
| 工程质量与开源规范 | 15 | 仓库结构规范 + 文档五件套 + `deploy.sh`/`test.sh` 一键复现 + 测试说明 |

## 三、五场景技术速查表（本项目的核心 cheat sheet）

| # | 场景 | eBPF 挂载点（参考） | 核心指标 | 诊断规则（示例） | 故障注入 | 难度 |
|---|---|---|---|---|---|---|
| 1 | 高频/高耗时 syscall 热点 | `raw_syscalls:sys_enter` / `sys_exit` | 每进程每 syscall 的频次、平均/P99 延迟 | 某进程某 syscall 频次 > 基线×10 且进 Top-N → `SYSCALL_HOTSPOT` | 自写 syscall bomb（循环 stat/open，30 行 C） | ★ |
| 2 | CPU 异常占用/调度延迟 | `sched_switch`、`sched_wakeup`；offcpu 统计 | runqlat 直方图、每进程 CPU%、off-cpu 等待时长 | 单进程 CPU > 80% 持续 10s → `CPU_HOG`；runqlat P99 > 基线×5 → `SCHED_DELAY` | `stress-ng --cpu` | ★★ |
| 3 | I/O 延迟抖动/阻塞 | `block:block_rq_issue` / `block_rq_complete` | 每进程/每设备 IO 延迟直方图、IOPS、队列深度 | 写延迟 P99 > 基线×5 → `IO_JITTER`，关联设备+进程 | `fio`（大 iodepth） | ★★ |
| 4 | 内存抖动/OOM 风险 | `oom:mark_victim`；缺页事件；`sys_enter_mmap`（长度） | 缺页速率、大块 mmap 统计、OOM 事件、每进程 RSS 增速 | 缺页率 > 基线×5 → `MEM_PRESSURE`；OOM 事件 → `OOM_KILL`（直接证据） | `stress-ng --vm` | ★★ |
| 5 | 锁竞争 | futex 系统调用进出 + offcpu 栈聚合 | 同一锁地址的等待线程数/时长、等待栈 | 同锁地址等待线程 ≥ N 且总等待时长超阈值 → `LOCK_CONTENTION`，输出锁地址+调用栈 | 自写 pthread 竞争程序（~50 行 C） | ★★★ |

> 挂载点名称以 `bpftrace -l` 在目标内核上实测为准（不同内核版本有差异——这本身就是 CO-RE/BTF 要解决的问题）。
> 实现顺序按难度递增：**1 → 2 → 3 → 4 → 5**。场景 5 的注入程序顺便当代码热身作业。

## 四、结构化输出契约（直接对齐评分字段）

评分细则要求输出至少包含：**异常类型、关联对象、关键指标、异常时间窗口、疑似根因、证据链、建议性结论**——JSON schema 照此设计：

```json
{
  "tool": "osmedic",
  "window": {"start": "2026-12-30T14:02:00+08:00", "end": "2026-12-30T14:03:00+08:00"},
  "anomalies": [
    {
      "type": "IO_LATENCY_JITTER",
      "confidence": 0.9,
      "related_objects": [
        {"kind": "process", "comm": "fio", "pid": 1950},
        {"kind": "device", "name": "vda"}
      ],
      "key_metrics": {"write_p99_ms": 180, "baseline_p99_ms": 8, "iops": 4200},
      "suspected_root_cause": "fio 高队列深度顺序写导致设备队列拥堵，业务写延迟被放大",
      "evidence_chain": [
        "14:02:01 起设备 vda 平均写延迟由 8ms 升至 45ms",
        "fio(pid=1950) 同期产生 92% 写请求",
        "业务进程 mysqld 写 P99 由 6ms 升至 180ms，时间窗口吻合"
      ],
      "recommendation": ["ionice -c3 限制 fio 权重", "错峰执行压测", "业务盘与压测盘分离"]
    }
  ]
}
```

这份契约 = 聚合层与规则引擎的接口规范 = 自动评测友好格式（评分细则明确说"便于机器解析得分更高"）。**阶段 3 开工前冻结此 schema。**

## 五、分阶段详解

### 阶段 0 · 环境热身（11/07 – 11/15）

**学什么**：Linux 命令行/包管理、git 协作流程、bpftrace 手感。

**任务清单**：

- [ ] 装 openEuler 24.03 LTS：虚拟机（VirtualBox/VMware，分配 ≥8G 内存）或云主机（华为云/阿里云 openEuler 镜像，约 ¥30–100/月，性能数据更可信）
- [ ] `dnf install -y bpftrace bcc-tools libbpf-devel clang llvm make git stress-ng fio sysstat kernel-devel`（个别包可能需要添加 EPOL 源）
- [ ] **第 1 天建公开仓库**（Gitee/GitHub 均可，最终同步 educg GitLab 用 https 协议）
- [ ] 玩 bpftrace 官网 one-liner tutorial 的 20 条命令（execsnoop、opensnoop、biosnoop、runqlat…）
- [ ] 克隆 `anakryiko/libbpf-bootstrap`，跑通 minimal 示例（追踪 execve）
- [ ] 确认报名：大赛平台报名、队伍信息、指导老师

**验收标准**：① bpftrace 一行命令能看到实时事件；② minimal 示例有输出；③ 仓库已有 ≥10 次提交（过程性资料开始积累）。

**常见坑**：虚拟机内存给少了（≥8G）；忘记 root/权限；内核头文件缺失装 `kernel-devel`；WSL2 不可用作主环境（BTF/CO-RE 支持不完整）。

### 阶段 1 · 探针基础（11/16 – 11/29，2 周）

**学什么**：libbpf 程序结构（`xxx.bpf.c` + 加载器）、Map/ring buffer、Verifier 报错怎么读、BTF/CO-RE 概念。资源：libbpf-bootstrap 源码、bpftrace 文档、《BPF Performance Tools》前几章。

**任务清单**：

- [ ] 把 minimal 示例改造成自写探针①：execve 追踪（进程启动事件 → ringbuf）
- [ ] 自写探针②：块设备 IO 延迟直方图（issue→complete 计时，map 存直方图）
- [ ] 用户态程序从 map 读数据，落盘成 JSON Lines 文件
- [ ] 每人独立复现一次（不看教程），能读懂 Verifier 的拒绝原因

**验收标准**：任一成员能独立"从零写一个带 ringbuf 的探针 + 落盘 JSON"。做到这一步，**eBPF 这道墙就翻过去了**。

**常见坑**：Verifier 拒绝（循环/栈超 512B/未初始化内存）→ 复杂逻辑移到用户态；tracepoint 字段名随版本变 → 以 `/sys/kernel/tracing/events/` 下格式定义为准。

### 阶段 2 · 五场景攻坚（11/30 – 12/20，3 周）

**节奏**：场景 1（2 天）→ 场景 2（3 天）→ 场景 3（3 天）→ 场景 4（3 天）→ 场景 5（4 天）→ 每场景留半天写文档小节。

**每个场景的完成定义（Definition of Done）**：

1. 探针稳定运行，数据进入聚合层；
2. `faults/` 下有对应注入脚本/程序，**能稳定复现该类异常**；
3. 该场景能输出一段"人能看懂"的摘要文本；
4. `docs/` 里该场景的设计小节写完。

**任务清单**（按速查表逐场景执行）：

- [ ] 场景 1：syscall 热点探针 + syscall bomb 注入程序
- [ ] 场景 2：runqlat/每进程 CPU 探针 + `stress-ng --cpu` 注入
- [ ] 场景 3：块 IO 延迟探针 + `fio` 压测注入
- [ ] 场景 4：缺页/OOM 探针 + `stress-ng --vm` 注入
- [ ] 场景 5：futex 等待 + offcpu 栈聚合探针 + 自写 pthread 竞争程序

**验收标准**：随机抽一个场景，能在干净环境一键复现"注入 → 工具看到 → 摘要输出"。

### 阶段 3 · 诊断引擎与结构化输出（12/21 – 12/28，1 周）

**任务清单**：

- [ ] 冻结 §四 的 JSON schema
- [ ] 采集正常负载基线（每场景跑 10 分钟正常态，存基线库）
- [ ] 规则引擎：阈值 + 基线对比 + 证据链组装（Python）
- [ ] CLI：`osmedic monitor`（常驻监控）/ `osmedic report`（出报告）
- [ ] 写 `test.sh`：五场景自动注入 → 自动判定诊断结果 PASS/FAIL

**验收标准**：`test.sh` 在五场景下全部 PASS——这就是评委复核的雏形，也是我们自己的回归测试。

### 阶段 4 · LLM 报告层（12/29 – 01/02）

**任务清单**：

- [ ] 接 API（DeepSeek/通义），prompt 只喂结构化证据（JSON），限定三段式输出（根因/证据/建议）
- [ ] 幻觉防线：LLM 结论与规则引擎结论做一致性比对；API 不通时降级为规则版报告
- [ ] 成本控制：仅异常触发时调用，正常监控零 API 消耗

**验收标准**：抽查 10 份 LLM 报告，根因/证据与规则引擎一致率 ≥90%。

### 阶段 5 · 收尾提交（12/28 – 01/04，与阶段 4 并行）

**任务清单**：

- [ ] **开销评测**（照评分细则四小项做对照表）：加载工具前后用 `pidstat`/RSS/`iperf3`/`fio` 对比 CPU、内存、时延、吞吐
- [ ] `deploy.sh` 一键部署 + `test.sh` 一键测试（找队友在**全新虚拟机**互测，模拟评委环境）
- [ ] 文档五件套：安装说明、使用说明、参数说明、设计说明、限制说明
- [ ] 演示视频 5–8 分钟（README 给链接）
- [ ] 按技术方案要求整理提交物，https 推送 educg GitLab

**验收标准**：全新 openEuler 虚拟机，30 分钟内从裸机到一键复现全流程。

### 决赛增量阶段（01/05 – 02 月中，按决赛通知）

- [ ] 插件化架构：探针注册机制（新场景 = 新插件，不改主程序）
