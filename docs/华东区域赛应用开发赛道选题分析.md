## 一、赛题回顾（技术方案原文要点）

应用开发赛道下设两个可选方向：

| 方向 | 内容 | 关键词 |
|---|---|---|
| **方向一：系统工具** | 基于开源操作系统（如 OpenEuler 等）开发系统工具 | 系统性能测试、功能测试、漏洞分析、软件调试、系统模拟器、移植工具等 |
| **方向二：应用程序** | 基于开源操作系统开发应用程序 | 独立小型应用、从其他 OS 移植应用、面向特定 OS 的优化 |

鼓励综合运用编译技术、操作系统、计算机体系结构等知识。

**提交内容**（评审导向的风向标）：

- 完整工程文件（源代码含注释、编译与环境构建文件）
- 设计文档：开发思路、各模块设计方案、**实现重点与创新点**、功能与性能测试情况（**包括与类似项目的对比分析**）
- **过程性资料**：各阶段过程性文档、开发历史、线上仓库提交记录
- 演示视频（README 中给链接）
- 在托管平台公开代码与文档（GitLab，https 协议推送）

**五年趋势规律（非常清晰）：**

1. **eBPF 观测/性能工具**：获奖密度最高的技术方向（2022 Eunomia → 2023 BoesFS/资源隔离 → 2025 AI/ML 追踪/用户态文件系统）
2. **AI × OS**：2025 年 8 个一等奖中 3 个与 AI 直接相关（LLM kdump 分析、AI/ML 负载追踪、可信 GPU 框架），是最新、最强的评审加分方向
3. **调试/异常检测工具**：2023 特等奖、2024 插桩工具、2025 Heap 检测，届届有奖
4. **国产架构移植**（LoongArch / 飞腾 / RISC-V）：2022–2025 届届拿奖，契合"高端芯片、关键基础软件后备人才"的办赛宗旨
5. **底座分布（重要澄清）**：国赛获奖作品**并非绑定 openEuler**——按底座归类，约 60% 是 Linux 内核生态（eBPF / 文件系统 / 锁 / 调试工具 / Hypervisor），约 25% 是移植类（LoongArch / 飞腾 / SylixOS / OneOS / seL4），约 15% 是嵌入式 RTOS / 教学 OS（如华东师大的 Cortex-M 实时 OS）。openEuler 是**华东区域赛**技术方案点名主推的底座（"如 OpenEuler 等"），属于区域赛的叙事加分项而非技术限制。eBPF / 观测类工具的技术内核就是 Linux，天然跨发行版——"主适配 openEuler + 兼容主流 Linux"是最优叙事。

## 三、方向判断：走方向一（系统工具）

**结论：优先选择"基于开源 OS 的系统工具"方向，不走"纯应用程序"方向。**

理由：

1. **评委构成决定口味**。赛题宗旨是系统能力培养，评委以 OS 课程教师与基础软件工程师为主。系统工具天然展示内核级深度（eBPF、perf、ptrace、/proc、crash dump 等）；纯上层应用很难回答评委必问的"这和操作系统有什么关系？"
2. **评分标准与技术方案要求高度匹配**。提交物明确要求"功能与性能测试情况（含与类似项目对比分析）"。性能/观测/调试工具自带可量化的 benchmark 与对比叙事（对比 top/strace/perf/bpftrace 等），"做一个 App"给不出这些。
3. **有五年成功范式可直接对标**。方向一可以站在国赛功能赛道已验证的获奖范式上做差异化，风险远低于自创选题。
4. **唯一例外**：方向二中"深度绑定 OS 特性"的选题（移植 + 优化、嵌入式边缘 AI、鸿蒙原生系统级应用）也有获奖实证，可作为备选；纯"小型应用程序"是下策。

## 四、选题方向建议（按推荐优先级排序）

### ★ 首选：eBPF × AI 的 openEuler 系统观测 / 故障诊断工具

- **示例题目**：《基于 eBPF + LLM 的 openEuler 性能观测与智能故障诊断平台》
  —— eBPF 采集系统指标 / 调用链 / IO 轨迹，LLM 做根因分析与调优建议输出
- **理由**：
  - eBPF 是 2022–2025 国赛一等奖最高频技术；
  - LLM × OS 是 2025 年最新获验证的获奖方向（哈工大深圳"黑天鹅"）；
  - openEuler 是技术方案点名 OS，社区有 A-Tune 智能调优等现成对比对象；
  - 性能工具天然自带"同类工具对比测试"数据，答辩硬气。
- **风险与对策**：eBPF 赛道较卷，必须靠"AI 分析层 + 场景化（如电力/服务器运维场景）"做差异化，避免做成 bpftrace 翻版。

### 次选：系统调试 / 异常检测工具

- **示例题目**：openEuler 上的内核异常 / 内存泄漏 / 死锁检测工具；或 RISC-V 平台系统级 trace 工具
- **对标**：2023 特等奖（Rust 内核调试工具）、2025 一等奖（Heap 异常检测）、2024 一等奖（QEMU 龙架构插桩）

### 国产架构移植 / 模拟器工具（零硬件可行：走 QEMU 模拟路线）

- **示例题目**：基于 QEMU 的 LoongArch / RISC-V 平台系统级工具（如插桩 / trace 工具）；或某教学 OS 的国产架构适配
- **对标**：2024 一等奖"基于 Qemu 的龙架构平台高性能插桩工具"（中科大）即为**纯软件方案**；seL4 LoongArch 移植（2022 一等奖）、xv6 VFS+HAL 跨 RISC-V/LoongArch（2026 国赛三等奖）同样可在 QEMU 上完成验证
- **说明**：无开发板时，国产架构方向全部可以走 QEMU 模拟路线，零硬件成本；**嵌入式开发板类选题（飞腾派智能小车、Jetson 边缘 AI 等）在无硬件条件下应直接排除**

### 差异化备选：鸿蒙方向

- OpenHarmony 原生的**系统级工具**（如基于分布式软总线的设备观测 / 调试工具）
- 或评估直接报名刚开设、几乎无人竞争的**鸿蒙专项赛道**（需先向组委会确认赛道细则与奖项设置）

### ❌ 避免

- 通用型 App（聊天 / 管理系统 / 笔记类）
- 与特定 OS 特性无关的纯算法项目
- 没有差异化对比价值的重复造轮子

### 硬件条件与环境方案（团队无专用硬件 —— 2026-10-26 补充）

首选方向（eBPF + LLM 工具）**本身就是纯软件项目，不需要任何专用硬件**，选题策略不变，仅做以下环境规划：

| 需求 | 方案 | 成本 |
|---|---|---|
| openEuler 运行环境 | 笔记本虚拟机（Hyper-V 装 openEuler 24.03 LTS，宿主机 ≥16G 内存、分给虚拟机 ≥8G；家庭版 Windows 用 VMware/VirtualBox 替代） | 0 |
| 更可信的性能数据 | 云服务器（华为云 / 阿里云 openEuler 镜像，2C4G 起），答辩用数据建议在固定云环境采集 | 约 ¥30–100/月 |
| eBPF 开发 | openEuler 24.03（内核 6.6）原生支持，需 root 权限 | 0 |
| LLM 分析层 | 调用 API（DeepSeek / 通义等），无需本地 GPU | 按量计费，很低 |
| 对比测试 | 同环境对比 bpftrace / perf / strace / top 等基线，取相对数据，文档注明测试环境 | 0 |

> ⚠️ 坑位提醒：WSL2 对 eBPF（BTF / CO-RE）支持不完整，开发环境优先用虚拟机或云主机，不要用 WSL2 做主环境。

## 六、零基础入门指南（概念速览 + 两周试跑计划）

### 6.1 概念速览（大白话版）

| 概念 | 一句话解释 | 类比（以计组知识为锚点） | 在本选题中的角色 | 实际学习成本 |
|---|---|---|---|---|
| QEMU | 开源"电脑模拟器"，用软件模拟一台完整计算机（CPU/内存/磁盘/网卡） | 计组实验的 RARS 模拟的是"一个处理器"；QEMU 把模拟做到"整台电脑 + 能装操作系统"级别 | **首选方向用不到**；备选方向（国产架构移植）用它当"软件开发板" | 2–3 天会装会用即可 |
| eBPF | Linux 内核的"探针"机制：把几十行小程序安全地挂进内核，在事件（系统调用/网络包/磁盘 IO）发生时自动记录数据 | 给 OS 装"行车记录仪 + 传感器"，不用拆发动机（不改内核源码、不写内核模块），有 Verifier 保证不会弄崩内核 | **首选方向的核心技术，唯一需要正经学的** | 1–2 周入门出原型 |
| LLM | 大语言模型，即 ChatGPT / DeepSeek / 通义千问这类 AI | — | **不训练模型、不碰数学**：只是 HTTP 调 API，把 eBPF 采集的数据发给它，要一份诊断报告 | 1–2 天 |

### 6.2 团队现有基础与所需能力的对应

- 计组（RISC-V）→ 已具备：C 语言、指令集/汇编、用户态/内核态切换概念
- OS 原理课 → 已具备：系统调用、中断、进程/内存/文件系统的概念模型
- 缺的只是"把这些概念接到 Linux 内核观测接口"这一步 = eBPF

### 6.3 两周试跑计划（定题前的零成本验证 / 决策门）

| 时间 | 目标 | 产出 |
|---|---|---|
| 第 1–2 天 | 装 openEuler 24.03 虚拟机/云主机，装 C 工具链，克隆 `libbpf-bootstrap` | 跑通 minimal 示例（追踪 execve）：实时看到"哪个进程启动了什么命令" |
| 第 3–5 天 | 用 bpftrace 玩 20 条单行命令 | 建立"一行代码出数据"的手感（execsnoop / opensnoop / biosnoop / runqlat） |
| 第 6–10 天 | 自写第一个探针（execve 追踪或 IO 延迟统计） | 理解三个概念（够用即可）：map（内核↔用户态传数据）、Verifier（安全审查）、CO-RE（跨内核版本运行） |
| 第 11–14 天 | 把数据落盘，做一个简易 CLI 报告 | **决策门：能独立写出探针 → 正式定题首选方向；仍很吃力 → 启动降级预案** |

> **降级预案**（两周试跑失败时，按优先级）：
> ① 砍范围——只做"eBPF 采集 + 规则诊断"（LLM 可最后再接，甚至不接）；
> ② 换"基于 openEuler 的实验教学体系"方向——技术最简单（shell/python + 自动化测试），有 SHIEP 全国三等奖实证，但叙事更偏"以赛促课"；
> ③ 转 OpenHarmony / 鸿蒙方向——应用开发路线，需补 ArkTS。
