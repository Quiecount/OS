## 一、eBPF 是什么：从"内核不允许随便动"说起

### 1.1 一句话定义

eBPF（extended Berkeley Packet Filter，扩展伯克利包过滤器）是 Linux 内核内置的**安全可编程机制**：允许你把自己写的一小段程序（**探针**），经过内核的严格安全检查后，**直接在内核里运行**，在系统事件发生的那一刻自动执行、采集数据——全程不改内核源码、不写内核模块、不重启系统。

### 1.2 它从哪来

- **1992**：BPF 诞生于 BSD，原本只是**网卡抓包过滤器**（决定哪些网络包复制给用户态程序）——名字里的"包过滤器"就是这么来的
- **2014**：Linux 3.18 把它大幅扩展成 eBPF，从"过滤包的工具"进化为"内核里的通用虚拟机"
- **今天**：eBPF 是 Linux 内核的正式子系统，有自己的峰会（eBPF Summit）和基金会；Facebook、Google、Netflix、Cloudflare、字节、华为云都在生产环境重度使用；openEuler 24.03（内核 6.6）原生完整支持

### 1.3 它是怎么工作的（5 步）

```
[用户态]                                 [内核态]
1. 编写：用受限 C 写探针（几十行），编译成 eBPF 字节码
        │
2. 加载 + 验证：bpf() 系统调用提交给内核
        │   Verifier 逐条指令模拟执行所有路径：
        │   不许越界访问内存 / 不许无限循环 / 必须快速终止
        │   只能调用内核预注册的 helper 函数
        │   → 不合规？直接拒绝，根本进不了内核
        │
3. JIT 即时编译：字节码 → 本 CPU 原生机器码（接近内核自身代码的执行效率）
        │
4. 挂载：挂到"插座"上（系统调用入口/内核函数/网卡收包路径……）
        │
5. 采数：事件发生 → 探针自动运行 → 数据写入 Map（内核里的键值仓库）
                          │
6. 用户态程序从 Map 读取 → 展示/分析 ←────┘
```

### 1.4 核心概念小词典

| 概念 | 大白话解释 |
|---|---|
| 探针（probe） | 你写的那段挂进内核的小程序 |
| Verifier | 内核"安检员"：加载前模拟执行每条路径，保证探针弄不崩内核 |
| JIT 编译 | 把探针字节码翻译成本机机器码，速度接近原生 |
| Map | 内核 ↔ 用户态的"数据仓库"（哈希表、环形缓冲、计数器……），探针写入、你的程序读取 |
| helper 函数 | 内核预先注册好的安全函数库，探针**只能**调这些，不能随便调内核任意函数 |
| 挂载点（hook） | 探针的"插座"：**kprobe**（任意内核函数进出）、**tracepoint**（内核官方埋点）、**uprobe**（用户态函数）、**XDP**（网卡驱动层收包，最快）、**LSM**（安全钩子）等 |
| CO-RE + BTF | "编译一次，到处运行"：靠内核自描述信息（BTF），同一探针可跨内核版本运行 |
| 开销 | 生产环境可常开：持续采集通常 < 1~2%（对比：strace 会把目标进程拖慢数倍） |

### 1.5 和你已会的工具对比

| 工具 | 能看到什么 | 缺陷 |
|---|---|---|
| top / /proc | 表面聚合指标（CPU%、内存占用） | 看不到"为什么"，看不到单条事件 |
| strace | 单个进程的每条系统调用 | 目标进程被拖慢数倍~数十倍，一次只能盯一个进程 |
| 内核模块（LKM） | 什么都能干 | 一个 bug = 整个内核崩溃；写法完全不受保护 |
| 改内核源码 | 什么都能干 | 要重编译、重启内核，生产环境不可能 |
| **eBPF** | **内核里几乎所有事件的逐条现场数据** | **安全、低开销、可热加载；代价是写法受 Verifier 约束** |

### 1.6 开发工具链（按上手难度从低到高）

| 工具 | 形态 | 适合 |
|---|---|---|
| **bpftrace** | 一行命令的 DSL（风格像 awk） | 建立直觉、快速排查，5 分钟出第一个数据 |
| BCC | Python 写用户态 + C 写探针 | 快速开发，运维工具多用它 |
| **libbpf / libbpf-bootstrap** | 纯 C，官方库 + 模板仓库 | **正式项目首选（我们走这条）** |
| aya | Rust 生态 | Rust 爱好者、前沿项目 |

### 1.7 典型应用场景

| 场景 | 用 eBPF 干什么 | 谁在用 |
|---|---|---|
| **可观测 / 性能分析**（我们选题用的） | 回答"慢在哪"：IO 延迟、CPU 等待原因、调用链、syscall 追踪 | Netflix、Facebook；bpftrace / BCC |
| 安全监控 | 抓无文件攻击、容器逃逸、异常提权 | Falco、Tracee、Wiz |
| 网络加速 | 网卡层丢包/负载均衡/DDoS 清洗 | Cloudflare、字节、Cilium |
| 策略控制 | 按进程/容器粒度的精细访问控制 | Tetragon |

### 1.8 限制与坑（提前知道）

- 加载探针需要 root（或 CAP_BPF 权限）
- Verifier 很严格：栈只有 512 字节、不能随意循环、单程序指令数有限 → **复杂逻辑放用户态，探针只做轻量采集**
- 部分功能依赖内核版本（建议 5.8+，openEuler 24.03 的 6.6 内核绰绰有余）
- 不能随意读内核任意数据结构，得借助 helper 和 BTF

### 2.2 重点案例深挖

#### 案例 1：AriadneTrace —— 唯一"eBPF + AI"合体的国一（2025 · 中山大学 · AAA逸仙os维修队）

**做了什么**：面向大模型训练/推理（vLLM 推理引擎）的性能追踪与智能瓶颈诊断系统。项目灵感来自 Meta 的 AI 观测基础设施（Dynolog 等）和 eBPF Summit 2023 的演讲。

**技术方案（自研部分）**：

| 层 | 用了什么 | 干什么 |
|---|---|---|
| 采集 | **eBPF**（内核侧）+ NVIDIA **CUPTI**（GPU 侧） | 抓 CUDA kernel 启动、流同步、显存访问等 GPU 事件 + CPU/系统行为 |
| 分析 | 基于开源 **Pyroscope**（持续火焰图）二次开发 | 自研 3 个迭代的 AI 分析模块（v1→v3），JSON 结构化预处理 |
| 智能 | **聚类模型 + 通义千问 Qwen**（阿里云 DashScope API） | 输出自然语言瓶颈诊断报告与优化建议，token 级瓶颈识别 |
| 展示 | Prometheus + Grafana | 可视化仪表盘 |

**创新点**：传统火焰图要专家人工看，它直接产出"哪里慢、为什么、怎么改"的报告；部署脚本一键搭起全套环境（vLLM + CUDA 容器 + 监控栈）；对目标应用**零侵入**。

**对我们的启示**：
1. "eBPF 采集 + LLM 分析"这个架构，评委已用国一投票认可；
2. 它走 **GPU/CUPTI 路线（必须有 NVIDIA 显卡）**——我们零硬件，做 **CPU/系统级运行时诊断**，正好**错位竞争**不撞车；
3. 它复用开源组件（Pyroscope/Prometheus/Grafana）+ 自研核心模块——聪明的工程策略，不必从零造轮子。

#### 案例 2：黑天鹅 —— "LLM 分析内核崩溃现场"国一（2025 · 哈工大深圳）

**背景**：kdump 是 Linux 的内核崩溃转储机制——内核 panic 时把整个内存现场快照存到磁盘，事后用 crash 工具分析。传统做法要资深工程师对着几十 GB 转储人工排查，门槛极高。黑天鹅用 **LLM 自动化这个过程**。

**他们走过的路**（队长原话要点）：
- 没有现成 baseline 可参考，从测评环境到整体框架，都是"参考多个仓库、阅读大量代码、改变接口最终缝合在一起"
- 队长 5 个月保持每天 8 小时以上投入
- 方法论（值得抄）：**明确问题（现状不足 + 根因）→ 方法的动机 → 方法 → 实验指标怎么证明解决了问题**——这条链想清楚，设计文档和答辩自然立得住

**对我们的启示**："LLM + 系统诊断"**单独就能撑起一个国一**——分析层的价值被评委高度认可，不只是采集层的附属品。

#### 案例 3：我重生了这一世我要夺回属于我的OS赛冠军 —— 大二零基础的国一（2025 · 哈工大深圳）

**做了什么**：轻量级**堆内存异常检测工具**，融合静态程序分析 + 动态程序分析 + **系统态异常检测**（"系统态"即内核视角观测，与 eBPF 同属内核侧思路）。

**最重要的事实**：三位队员组队时**均为大二（23 级），"大多没有操作系统相关的经验"，抱着试一试的心态参赛，拿了全国一等奖。**

**他们走过的路**：简单静态分析工具 → 动静结合 → 用户态+系统态结合，经历**多次大重构**——每重构一次，对项目的理解就深一层。

**对我们的启示**：零基础不是劣势，是往届国一队伍的常态。获奖靠的是：选题聚焦 + 多轮迭代 + 老师指导 + 坚持。

#### 案例 4：FastPoke —— eBPF 玩到文件系统层的国一（2025 · 哈工大深圳）

**做了什么**：用内核态/用户态 eBPF 加速 FUSE（用户态文件系统）的 I/O 路径，并仿真 CSD 智能存储设备。

**他们踩过的坑（原话）**：
- "eBPF 程序开发受验证器严格限制，需要在内核提前注册 eBPF helper 函数来辅助实现复杂功能"——Verifier 那堵墙真实存在
- FUSE I/O 绕过：缓存命中率不稳定；直通路径有内核数据/文件数据**泄漏风险**，要做边界保护
- CSD 硬件不成熟，只能改 SSD 模拟工具来做仿真

**给下一届的建议（原话）**："尽早确定方向与架构……**有时候选择比努力更重要**""别想那么多，干就完了"。

**对我们的启示**：eBPF 的天花板极高（改文件系统 I/O 路径都行），但硬核玩法要付硬核成本。观测/诊断层是 eBPF 难度带里**性价比最高**的区间。

#### 案例 5：BoesFS —— eBPF 沙箱文件系统（2023 一等奖 · 哈工大深圳）

- "Based on eBPF Sandboxing Filesystem"：在 VFS 层用 eBPF 做轻量级文件安全沙箱，应用于 FaaS 场景
- 5 个月产出：**近 2 万行代码 + 12 万字维护文档**
- 选题逻辑（原话）："eBPF 近年大火 + 和传统文件系统结合，或许能有不一样的花火"——**老技术 × 新热点的组合**就是创新点

**对我们的启示**：评委对文档的重视远超想象——12 万字文档不是负担，是他们国一作品的组成部分。

#### 案例 6：Eunomia —— eBPF 观测的国赛开山作（2022 一等奖 · 浙江大学 · 牛校牛子队）

- C/C++ 开发的轻量级云原生**容器监控框架**：容器全生命周期行为观测 + 可疑安全事件监控 + Prometheus 集成
- 赛后成长为真实开源社区（github.com/eunomia-bpf），衍生出 WASM + eBPF 运行时等后续工作
- **对我们的启示**：竞赛项目可以长成开源社区，这是"以赛促学"的天花板形态；同时它也是我们工具天然的**对比对象**（同类工具对比测试是评分硬要求）

## 三、eBPF 与 AI 到底是怎么结合的

看完案例，最自然的问题就是："eBPF 在内核里，AI 在云端/用户态，它们俩隔着好几层，怎么就'结合'了？"——答案是：**两者根本不直接对话，中间有一条数据流水线；eBPF 负责"把真实数据采上来"，AI 负责"把数据翻译成人话和结论"**。下面把这件事彻底讲透。

### 3.1 为什么这两个技术是"天作之合"：分工互补

| | eBPF | LLM / AI |
|---|---|---|
| 解决的问题 | **数据从哪来**：内核级、逐条事件、低开销、零侵入 | **数据意味着什么**：知识、经验、解释、建议 |
| 类比 | 感觉神经 / 传感器 | 大脑 |
| 单独用的困境 | 数据很真很细，但只有专家看得懂——"有一堆仪表盘，没人会读" | 有知识有口才，但没有可靠数据可分析——"瞎子算命"，容易一本正经地胡说 |

**两者结合 = 给大脑接上了高保真的感觉神经。** 这就是为什么 AriadneTrace 把两者拧在一起能拿国一：它先用 eBPF 保证"喂给 LLM 的每个数字都是内核里真实发生的"，再用 LLM 保证"专家级分析结果人人看得懂"。

### 3.2 标准数据流水线（五层架构，结合的本质就是它）

```
┌──────────────────────────────────────────────────────────────┐
│ ① eBPF 探针层（内核态，C）                                    │
│    execve / 磁盘IO / 系统调用 / 调度事件 → 逐条原始事件        │
├──────────────────────── ring buffer / map ──────────────────┤
│ ② 采集代理层（用户态，C）                                     │
│    把事件从内核读出来、初步过滤（丢无关进程/采样）              │
├──────────────────────────────────────────────────────────────┤
│ ③ 聚合与特征层（用户态，Python 等任意语言）   ★ 关键的一层     │
│    把"事件洪流"压缩成"系统画像"：每进程 CPU/IO/延迟分布、      │
│    异常点标记、时间窗口统计 → 输出 JSON 快照                   │
├──────────────────────────────────────────────────────────────┤
│ ④ 决策/触发层（规则引擎：阈值、基线对比）      ★ 省钱的一层    │
│    判断"要不要惊动 AI"：正常时只记录，异常时才往上传            │
├──────────────────────────────────────────────────────────────┤
│ ⑤ LLM 分析层（HTTP 调 API）                                  │
│    prompt = 系统画像 + 异常证据 → 诊断报告 + 优化建议          │
└──────────────────────────────────────────────────────────────┘
```

各层存在的理由（**跳过任何一层都会翻车**）：

| 层 | 存在的理由 | 跳过它的后果 |
|---|---|---|
| ② 采集代理 | eBPF 数据在内核里，总得有人取出来 | — |
| ③ 聚合特征 | eBPF 每秒可能产出**几十万条事件**，LLM 上下文只有几十万 token | 直接喂原始事件：数据量爆炸、API 费用爆炸、效果还差 |
| ④ 决策触发 | 每分钟都调 LLM 又贵又慢 | 系统正常时也乱花钱；真正异常时反而淹没在噪音里 |
| ⑤ LLM | 规则只会说"超阈值了"，不会说"为什么、怎么办" | 用户拿到报警还是得自己当侦探 |

### 3.3 三种结合模式（按成熟度排序）

**模式一：eBPF 采集 + LLM 诊断报告**（AriadneTrace / 黑天鹅路线，**我们选这条**）

流程就是上面 3.2 的五层流水线。LLM 在这里扮演"自动化专家"：输入结构化证据，输出根因分析 + 建议。黑天鹅的 kdump 场景是这个模式的"崩溃后"特例（数据源从实时观测换成崩溃转储）。

**模式二：eBPF 采集 + 传统机器学习异常检测**（LMY 2022、AriadneTrace 中的聚类模块、openEuler A-Tune）

在③层之后不用 LLM，而用聚类/异常检测模型（K-Means、Isolation Forest 等）做**自动异常发现**——便宜、快、可常开。但输出是"分数/分类"，不是人话。**实战中常与模式一两段式配合**：ML 全天候盯着 → 发现异常 → 才把这段数据交给 LLM 深度解释。

**模式三：AI 反向生成 eBPF**（前沿探索方向）

方向反过来：用自然语言描述"我想看看哪个进程在读写这个文件"→ LLM 生成 bpftrace/eBPF 探针代码 → 加载运行。Eunomia 社区等已有探索。对我们：可作为工具里的**加分亮点功能**（"对话式观测"），但**不要当主线**——把探针生成交给 LLM 有安全风险（生成坏探针加载会被 Verifier 拒绝，调试成本高）。

### 3.4 一个完整的例子（把流水线从头到尾走一遍）

场景：**一台 openEuler 服务器突然变卡**。我们的工具五层各干什么、产出什么——

**① eBPF 探针层采到的原始事件**（节选，实际每秒几万条）：

```
14:02:01  mysqld     pid=2841  磁盘写 4096B  延迟 45ms   ← 异常！基线只有 4ms
14:02:01  python3    pid=1947  execve("/usr/bin/backup.sh")
14:02:02  backup.sh  pid=1950  磁盘读 1MB    延迟 120ms
14:02:02  backup.sh  pid=1950  CPU状态=IO等待(92%)
...
```

**③ 聚合特征层产出的"系统画像"JSON**（这一步把几万条压缩成几十行）：

```json
{
  "时间窗口": "14:02:00 - 14:03:00",
  "IO":  { "平均写延迟_ms": 45, "P99_ms": 180, "热点进程": "mysqld(2841)" },
  "CPU": { "负载": 0.8, "最大IO等待进程": "backup.sh(1950), 等待占比92%" },
  "异常点": ["mysqld 写延迟较基线(4ms)飙升10倍", "backup.sh 于14:02:01启动"]
}
```

**④ 决策层**：规则判断"写延迟超基线 5 倍"→ 触发 AI 分析。

**⑤ 发给 LLM 的 prompt**（就是一条 HTTP 请求）：

```
你是 Linux 性能诊断专家。以下是某 openEuler 服务器 1 分钟内由
eBPF 采集聚合的系统观测快照：{上面的 JSON}
请分析性能瓶颈：1) 根因判断  2) 支撑证据  3) 处理建议。
```

**LLM 返回**（工具把它渲染成报告/告警）：

```
诊断：磁盘 IO 争用。根因是 14:02:01 启动的备份脚本 backup.sh 与
业务进程 mysqld 抢占磁盘带宽。
证据：mysqld 写延迟从基线 4ms 飙至 45ms，时间与 backup.sh 启动
精确吻合；backup.sh 自身 92% 时间处于 IO 等待。
建议：① 用 ionice/cgroup 限制备份进程 IO 权重；② 将备份任务
移至业务低峰期；③ 考虑为 mysqld 数据目录换用独立存储。
```

**看到了吗：从"服务器卡了"到"专家级诊断 + 可执行建议"，全程无人值守、零侵入、开销近零。这就是"eBPF + AI"的全部秘密。**

### 3.5 结合时的四个工程挑战（也是答辩时评委最可能追问的）

| 挑战 | 问题 | 对策 |
|---|---|---|
| **数据量鸿沟** | eBPF 事件洪流 vs LLM 上下文有限 | ③聚合层是生命线；按时间窗口/进程维度压缩 |
| **成本** | 每次分析都调 API，烧钱 | ④规则触发层：正常时静默记录，异常才调用 |
| **幻觉** | LLM 可能一本正经地瞎诊断 | 只喂结构化证据；限定输出格式（根因/证据/建议三段式）；关键结论用规则引擎交叉验证 |
| **时延** | 实时告警等不了 LLM 几秒响应 | 分层：规则层做秒级实时告警，LLM 做深度诊断报告 |

### 3.6 落到我们项目

- **架构直接采用 3.2 的五层流水线**——这一节本身就是我们设计文档"系统架构图"的草稿；
- **技术上采用"模式二 + 模式一"两段式**：规则/统计全天候监控（免费、实时），LLM 异常时深度诊断（按需调用）；
- 各层选型：①②libbpf + C（两周试跑目标）、③④Python（最容易写）、⑤DeepSeek/通义 API（1–2 天上手）；
- 每一层都是一个独立的里程碑——**做完任何一层都是一个"能演示的东西"**，进度永远不会陷入"全部写完才能看"的险境。

## 四、把获奖经验拼成我们的路线图

1. **选题定位在"已验证交集"**：eBPF 观测（Eunomia/BoesFS/FastPoke 连续 4 年获奖）× LLM 诊断（黑天鹅/AriadneTrace 连续获奖）= 我们的"eBPF 采集 + LLM 分析"
2. **差异化**：AriadneTrace 做 GPU/AI 负载（要显卡）、黑天鹅做崩溃后分析（kdump）；我们做 **CPU/系统级、运行时性能诊断**（零硬件、通用场景）——三者错位，不撞车
3. **工程策略照抄 AriadneTrace**：复用成熟组件（libbpf + 现成的可视化方案），自研核心（探针集合 + LLM 诊断流水线），环境搭建脚本化
4. **文档策略照抄 BoesFS**：边开发边写，设计文档 + 维护文档双轨推进，别等做完了再补
5. **方法论照抄黑天鹅**：先把"解决什么问题 → 为什么现有方案不够 → 我们的方法 → 怎么证明有效"想清楚，开发再动手
6. **心态照抄"我重生了"队**：大二零基础能拿国一，靠的是聚焦、迭代、坚持——我们现在的起点不比他们差
