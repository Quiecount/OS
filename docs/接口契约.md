## 一、接口 A：探针 ↔ 加载器（已冻结）

- 载体：每个探针自带名为 `events` 的 ringbuf map（256KB）
- 结构：见 `src/events.h`——所有场景事件以 `ev_common`（ts_ns/pid/uid/comm）开头，场景字段随后
- **演进规则：只允许在结构体尾部追加字段**；禁止改名、改类型、中部插入

## 二、接口 B：加载器 → 标准输出 = JSON Lines（核心契约）

### 2.1 通道与编码

| 通道 | 内容 | 规定 |
|---|---|---|
| **stdout** | **仅 JSON Lines**：每行一个 JSON 对象，UTF-8 | 管道下游（collector）只消费 stdout |
| **stderr** | 人类提示：表头、"按 Ctrl+C 退出"、错误信息 | 永远不进管道 |
| 退出码 | 0 = 正常结束（含 Ctrl+C / --duration 到时）；1 = 错误 | 脚本可判 |

> execsnoop 已落实“默认 JSONL 到 stdout、`--pretty` 时表格到 stdout”，并支持 `--duration N`；
> 2026-11-19 在 openEuler 24.03 LTS 通过集成验证。其他场景加载器仍随阶段 2 逐项实现。

### 2.2 公共字段（所有场景每行必有）

| 键 | 类型 | 说明 |
|---|---|---|
| `scene` | string | 场景代号，枚举：`exec` `syscall` `cpu` `io` `mem` `lock` |
| `ts_ns` | number | 内核时间戳（纳秒，`bpf_ktime_get_ns`） |
| `pid` | number | 进程 ID |
| `uid` | number | 用户 ID |
| `comm` | string | 进程名（≤15 字符） |

### 2.3 场景特有字段（追加在公共字段后）

| scene | 键 | 类型 | 说明 |
|---|---|---|---|
| `exec` | `filename` | string | 被执行的程序路径 |
| `syscall` | `id` | number | 系统调用号 |
| `cpu` | `prev_pid` / `next_pid` | number | 切换前 / 后进程 |
| `io` | `delta_ns` | number | issue→complete 延迟；骨架期为 0 |
| `mem` | `addr` | **string(hex)** | 缺页地址，如 `"0x7f3a2b000"` |
| `lock` | `uaddr` | **string(hex)** | futex 锁地址（**必须 hex 字符串**，见下） |
| `lock` | `op` | number | futex 操作码 |

> **为什么地址用 16 进制字符串**：64 位地址超出 JSON number 的安全整数范围（2^53），直接当数字会丢精度——地址类字段一律 `"0x..."` 字符串。

### 2.4 示例行

```jsonl
{"scene":"exec","ts_ns":1763350000123456789,"pid":3041,"uid":0,"comm":"bash","filename":"/usr/bin/ls"}
{"scene":"syscall","ts_ns":1763350000123456801,"pid":3041,"uid":0,"comm":"bash","id":4}
{"scene":"cpu","ts_ns":1763350000123500000,"pid":10,"uid":0,"comm":"swapper","prev_pid":3041,"next_pid":3055}
{"scene":"io","ts_ns":1763350000130000000,"pid":1950,"uid":0,"comm":"fio","delta_ns":45000000}
{"scene":"mem","ts_ns":1763350000140000000,"pid":4001,"uid":1000,"comm":"stress-ng","addr":"0x7f3a2b000"}
{"scene":"lock","ts_ns":1763350000150000000,"pid":5002,"uid":1000,"comm":"lock_content","uaddr":"0x7ffd1c4a8","op":0}
```

### 2.5 加载器命令行（阶段 2 起统一支持）

```text
<loader> [--duration N] [--pretty]
  --duration N   采集 N 秒后自动退出（默认：无限，Ctrl+C 退出）
  --pretty       人类可读表格输出到 stdout（默认 JSONL）
```

## 三、接口 C：注入脚本（faults/）

- 调用形式：`./faults/0N_<场景>.sh [时长秒]`，时长默认 60
- 输出：进度提示到 stdout（仅供人看，不参与管道）
- 行为：内置依赖检查，缺工具时打印安装命令并以退出码 1 结束；正常结束退出码 0

## 四、接口 D：collector（analysis 层）输入/输出

### 输入

- `--input FILE` 或 stdin；内容 = 接口 B 的 JSON Lines
- `--window N`：统计窗口秒数（默认 60）

### 输出：七字段诊断报告（stdout，单一 JSON 对象）

| 字段 | 类型 | 必有 | 说明 |
|---|---|---|---|
| `tool` | string | ✓ | 固定 `"osmedic"` |
| `window.start` / `window.end` | ISO8601 | ✓ | 观测时间窗 |
| `anomalies` | array | ✓ | **无异常时为空数组 `[]`（不是省略）** |
| `anomalies[].type` | string 枚举 | ✓ | 见 4.1 |
| `anomalies[].confidence` | number 0–1 | ✓ | 规则置信度 |
| `anomalies[].related_objects[]` | array | ✓ | 元素 `{kind, ...}`，kind ∈ `process` `thread` `syscall` `device` `file` `lock` |
| `anomalies[].key_metrics` | object | ✓ | 键名见 4.2 |
| `anomalies[].suspected_root_cause` | string | ✓ | 一句话根因 |
| `anomalies[].evidence_chain[]` | string[] | ✓ | 每条 = 一项可核查的证据 |
| `anomalies[].recommendation[]` | string[] | ✓ | 可执行建议 |

### 4.1 异常类型枚举（与场景一一对应）

| 场景 | type |
|---|---|
| syscall | `SYSCALL_HOTSPOT` |
| cpu | `CPU_HOG` / `SCHED_DELAY` |
| io | `IO_JITTER` |
| mem | `MEM_PRESSURE` / `OOM_KILL` |
| lock | `LOCK_CONTENTION` |

### 4.2 key_metrics 必含键（按 type）

| type | 必含键（均为 number，地址/名称除外） |
|---|---|
| `SYSCALL_HOTSPOT` | `calls_per_sec`, `baseline_calls_per_sec`, `top_syscall_id`, `top_pid` |
| `CPU_HOG` | `cpu_percent`, `pid` |
| `SCHED_DELAY` | `runqlat_p99_ns`, `baseline_p99_ns` |
| `IO_JITTER` | `p99_ns`, `baseline_p99_ns`, `iops`, `device`(string) |
| `MEM_PRESSURE` | `faults_per_sec`, `baseline_faults_per_sec`, `top_pid` |
| `OOM_KILL` | `victim_pid` |
| `LOCK_CONTENTION` | `wait_ns_total`, `waiter_count`, `uaddr`(string-hex) |

## 五、接口 E：test.sh 自动判定（阶段 3 实现）

流程约定：启动加载器 → 跑 `faults/0N_*.sh` → collector 出报告 → 断言 `anomalies[].type` 含预期值。

| 注入脚本 | 预期 type |
|---|---|
| 01_syscall | SYSCALL_HOTSPOT |
| 02_cpu | CPU_HOG（或 SCHED_DELAY） |
| 03_io | IO_JITTER |
| 04_mem | MEM_PRESSURE |
| 05_lock | LOCK_CONTENTION |

判定输出：每场景一行 `[0N_场景] PASS/FAIL`，任一 FAIL 则整体退出码 1。

## 八、v1.1 增量：高频场景的聚合快照

场景 1、2 的每次 syscall 或调度事件都写入 256 KB ringbuf 会放大复制与丢事件风险，因此这两个探针在内核 map 中聚合，由加载器每个窗口读取并输出 JSONL。`src/events.h` 的 v1.0 原始事件结构保持不变，仍供低频事件和其他场景使用；`syscall_hotspot`、`cpu_hog` 使用 `src/common/osmedic.h` 的 map 结构作为新增 A 接口。

窗口行在 v1.0 的 `scene`、`ts_ns`、`pid`、`uid`、`comm` 公共字段后追加 `event` 与 `window`。`ts_ns` 取用户态 `CLOCK_MONOTONIC` 快照，与内核 `bpf_ktime_get_ns` 同一时钟域。`event` 可为 `syscall_metric`、`cpu_metric`、`scheduler_metric` 或 `diagnosis`。聚合行不表示一次原始 `sched_switch`，因此 CPU 聚合行没有 `prev_pid` / `next_pid`；syscall 行保留 `id`。其他指标作为附加字段输出。

`diagnosis` 行追加 `type`、`related_objects`、`key_metrics`、`suspected_root_cause`、`evidence_chain`、`recommendation`。`analysis/collector.py` 将其汇总到 v1.0 的 `anomalies[]`，补 `confidence=1.0` 表示规则条件已命中；这是规则匹配值，不是根因概率。三类异常的 `key_metrics` 保持 §四 4.2 的必含键。

阶段 2 的这两支加载器支持 `--duration`、`--interval`、`--output` 与阈值参数，默认 stdout 仅 JSONL。`--pretty` 仍待与其他场景加载器一起统一实现。

CPU 百分比口径修正：`cpu_metric.cpu_percent_one_core` 和 `CPU_HOG.key_metrics.cpu_percent` 由 `/proc/PID/stat` 的 utime + stime 在相邻窗口的差值计算，单核为 100%，进程多线程总和可超过 100%。进程启动时间用于区分 PID 复用；采样间隔内创建并退出的短进程可能没有 CPU 样本。调度等待、runqlat 直方图及 SCHED_DELAY 仍由 eBPF sched 事件聚合，不受 CPU 百分比来源改变影响。

## 九、v1.2 增量：精细延迟与完成的 off-CPU 区间

- `histogram="log2_8_ns"` 表示纳秒单位、每个 2 的幂区间细分 8 桶，共 384 桶。桶边界由 `src/common/latency_hist.h` 定义，不能再按 `2^index` 解读。`p99_upper_us`、`runq_p99_upper_us` 仍以微秒输出上界，向上取整；新增 `p99_overflow` / `runq_p99_overflow` 标志，出现溢出时不可把数值当作有限上界。
- syscall 的 `--histogram` 可额外输出 `latency_buckets`，用于独立参考验证；默认不输出大数组。CPU 的 `runq_buckets` 改为同一细分格式，消费方须检查 `histogram` 标识。
- `SYSCALL_SLOW` 是独立诊断：同一 PID/syscall 完成样本数 ≥ `--slow-min-samples`（默认 20）且平均耗时 > `--slow-us`（默认 10000 μs）。不要求进入频率 Top-N。`key_metrics` 包含 `mean_us`、`p99_upper_us`、`threshold_us`、`samples`。预期等待调用（sleep、futex、poll/select/epoll、wait4）保留指标但不触发此通用慢调用规则。慢 read/open 等仍需结合业务语义解释，不代表每次阻塞都是故障。
- CPU 指标新增 `offcpu_completed_ms`、`offcpu_completed_samples`。范围是线程切出到再次切入的完整时间，包含运行队列等待和睡眠/阻塞；按进程对线程求和，因此可以超过窗口墙钟时长。一个跨窗口区间归入其**结束窗口**，尚未结束的区间不计入；这不是实时等待存量，也不是把每段等待精确切分到各个窗口。不得将该字段当作每秒 off-CPU 使用率。
- syscall 快速计时采用每 CPU 缓存；发生 sched_switch 时将未完成调用转存到 TID 表，退出可跨 CPU 回收。已有 `sys_enter/sys_exit` 与线程退出挂载点保留，新增 sched_switch 挂载点只服务计时状态迁移。
- `quality_reference` 是评测专用探针，输出逐事件参考样本。生产加载器不加载它；吞吐评测不得同时启用参考探针，以免混入参考采集开销。

### 2026-11-20 窗口合并与归因修正

- 一个输出窗口内，同一 PID/syscall 或 PID 的多段 map 快照先合并，再排序、输出和更新告警状态。CPU 使用率只赋值一次，不再输出同 PID 的零运行时间碎片。
- `SCHED_DELAY` 的 `pid`、关联进程、`key_metrics.runqlat_p99_ns` 与 `samples` 全部来自同一进程的等待统计，不再将全机 P99 归因给等待总量最大的进程。全机 P99 继续通过 `scheduler_metric` 输出。
- syscall 默认 PERCPU_HASH，加载器聚合全部可能 CPU 的值；`--shared-stats` 使用共享 HASH 和原子更新。两种模式的计数、延迟及 JSON 单位相同，均未采用采样；内核 map 内存不同。
- 这一轮 sched_switch 读取 Linux 6.6 的第 4 个参数 prev_state，并结合 preempt 识别可运行状态；后续移植 5.10 时须适配挂载参数，当前不宣称已兼容。

### 2026-11-21 采样区间与精确阈值（2026-11-22 已完成 root 复测）

- CPU 指标追加 `cpu_sample_start_ns`、`cpu_sample_end_ns`（CLOCK_MONOTONIC）、`cpu_read_span_ns`（本次 /proc 读取耗时）、`cpu_sample_valid`。CPU 百分比为累计时间差除以上述实际采样间隔；窗口 start/end 仍表示汇总窗口，ts_ns 仍表示输出时刻。新 PID 首次读取仅建立基线，无有效区间时 valid=false、CPU 值为 0，不得把它解释为已测得空闲。精度评测必须使用有效采样起止时间，不能用输出时刻对齐。
- `runq_over_threshold_samples` 为实际等待严格超过 `runq_threshold_ns`（配置基线×5）的样本数。SCHED_DELAY 仍要求 ≥20 样本，但使用精确尾部计数判断 nearest-rank P99 是否超过阈值，条件为超过阈值样本数 > floor(总样本数/100)。诊断 key_metrics 追加 over_threshold_samples、threshold_ns；runqlat_p99_ns 仍是直方图上界估计，不是精确数值。
