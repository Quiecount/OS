## 五、发现与观察

### 5.1 lock_top 单指标排序会把"周期性睡眠"排在"真锁竞争"前（非缺陷，规则引擎输入实证）

本轮聚合中，两个 systemd 类周期性 1s futex 睡眠锁（`wait_ns_total` ≈ 13s，`waiter_count=1`）在 lock_top 中排在注入锁（`wait_ns_total` ≈ 2.7s，`waiter_count=8`）**之前**——因为 lock_top 按 `wait_ns_total` 排序，而周期性睡眠的累计时长轻松超过高频短等待的竞争锁。

这正是阶段 3 规则引擎已确立的设计约束的实证：**LOCK_CONTENTION 判定必须合取（同锁等待线程数 ≥ N 且总等待时长超阈值）**，按任何单一指标排序/判定都会把 systemd 类周期性睡眠误报为锁竞争。本测试为该约束提供了真实数据支撑。

- 宿主机重启导致 Hyper-V 默认交换机网段漂移（172.29.x.x → 172.24.80.0/20），VM 新 IP `172.24.87.47`，SSH 配置已更新；
- `faults/05_lock.sh` 经 scp 传输带 CRLF 导致 shebang 失效，VM 内 `sed -i 's/\r$//'` 修复后正常——与既有工作流结论一致（根治靠 git bundle 同步）。

### 7.3 延迟偏差分析：唤醒调度延迟，非探针缺陷

两档偏差均为**系统性正偏差**（实测恒大于真值），且绝对量级相近（1ms 档 ~135µs、5ms 档 ~150µs）、相对误差随 timeout 增大而缩小。定位：

- 探针测的是 `sys_enter_futex → sys_exit_futex` **墙钟时长**（futex 观测的标准语义，bpftrace 同款）。timeout 到期后线程还要经历"hrtimer 唤醒 → 进运行队列 → 被调度执行 → syscall 返回"，这段**唤醒调度延迟**包含在 exit 时刻里；
- 校准程序 4 线程几乎同时到期、同时唤醒，在 vCPU 受限的 VM 中排队放大了该延迟（1ms 档 4 线程偏差 > 5ms 档 2 线程，与线程数一致）；
- 从被观测线程的用户态视角看，它确实等了这么久才从 syscall 返回——测量语义本身正确。若阶段 3 需要"纯内核等待时长"，可挂 sched_wakeup 对齐计算（打磨期增强项，已登记规划 §七）。

### 7.5 极限吞吐损失与 WAIT-only 优化实验

微基准：`tests/futex_bomb.c`——单线程 FUTEX_WAKE 洪泛（无等待者，内核最快路径），开/关探针对比每秒次数：

| 配置 | 轮次 | wake/s |
|---|---|---|
| 关探针 | 2 轮 | 6.87M、7.01M（均值 6.94M） |
| 开探针·全 op 配对（旧默认） | 2 轮 | 3.27M、2.98M（均值 3.13M）→ **损失 54.9%** |
| 开探针·WAIT-only 过滤（新默认） | 3 轮 | 5.48M、4.31M、4.51M（均值 4.77M）→ **损失 31.3%** |

- **实验动机**：量化数据揭示 WAKE 类操作根本不睡眠，enter/exit 对它做 map 配对纯属浪费——高频 WAKE 下 enter 的 map 写入是探针开销大头；
- **实验结果**：enter 探针加一条命令码过滤（仅 FUTEX_WAIT / FUTEX_WAIT_BITSET 计时），极限吞吐提速 +52%；两组数据完全不重叠（WAIT-only 最差轮 4.31M > 全 op 最好轮 3.27M），提速稳定，**设为默认**（探针改动已回写规划文档 §2.3）；
- **回归**：WAIT-only 下 Verifier 通过、校准计数仍 0 误差、延迟分布与全 op 一致（7.2 第二列）、检出正常（7.4）——语义无损（场景5 只关心等待，WAKE 不睡、配对计时无意义）；
- **边界说明**：54.9%/31.3% 来自不停调用 futex 的极限微基准（~7M 次/秒），不能直接解释为真实业务都会下降同比例——正常程序 futex 频率远低于此，实际影响待阶段 3 基线对比量化。5% 类工程目标：未查到赛事规定的统一优秀线，暂不设挑战值。

### 8.2 方法1：Python GIL 争用（`tests/gil_bomb.py`）

负载：8 线程纯 Python 计数 20s（观测 26s）——线程反复争抢 CPython 解释器的 GIL，等待发生在 futex 上，是**未经任何注入的真实程序行为**。

- 8 线程版：30951 事件中 30899 来自 python3；top2 锁 `0x7f3127d1630c`（15361 次，waiter_count=9，累计 69.826s）与 `0x7f3127d16308`（15284 次，9，69.433s）——**两地址仅差 4 字节，正是 CPython `_gil_runtime_state` 中相邻的 mutex/cond 对**；waiter_count=9 = 8 个 worker + 1 个主线程（主线程在 start/join 间隙也要跑字节码、同样争 GIL）；
- 同窗捕获到主线程 join() 阻塞：单次等待 19.881s（waiter_count=1，合取规则正确不告警）——**一次观测同时看到"真竞争"与"长但不竞争"两类信号**；
- 单线程对照版：告警消失。python3 仅 2 事件（join 19.995s + 启动握手 5.101ms），无任何 waiter_count ≥ 2 的锁。

### 8.3 方法2：真实构建负载（make -j8 × 100 轮全量重编）

负载：`make clean && make -j8` 连续 100 轮（38.735s real / 1m58.8s user），每轮含 bpftool BTF dump、6 次 clang BPF 编译（含 12 万行 vmlinux.h）、8 次 gcc、2 次链接——模拟 CI 反复构建的真实负载，观测窗口覆盖全程。

- 默认阈值（100µs）：83 事件全部来自系统守护进程（tuned 周期性 1s 睡眠 ×82、in:imjournal ×1），**合取判定不触发，零误报**；
- 降阈值至 1µs（全景复核）：77 事件仍全部为守护进程——**约 600 次 make/cc1/clang/ld 调用没有产生任何一个 ≥1µs 的 futex 等待**；
- **预期修正**：原判据"捕获进程名（cc1/ld/make）符合预期"隐含了"构建进程会出现在 futex 等待中"的假设，实测证伪——单线程程序（编译器/链接器/make）不共享锁、不睡 futex，这是确定性的系统行为而非工具盲区。方法2 的有效判据据此修正为：**真实负载下进程名与实际活动一致（捕获到的 tuned/in:imjournal/rs:main 均为真实守护进程）、等待时长量级合理（周期性 1s 睡眠模式）、CPU 密集但锁健康的负载不误报**——全部达成；
- 该结果与方法1 互为反面证据：工具不会把"系统很忙"误读为"锁竞争"，告警只由真实的锁排队触发。

### 8.5 本轮结论与现实意义
