```bash
sudo dnf install -y gcc clang llvm make bpftool libbpf-devel \
  pkgconf-pkg-config elfutils-libelf-devel zlib-devel
```

```bash
sudo dnf \
  --repofrompath=stage1-everything,https://mirrors.huaweicloud.com/openeuler/openEuler-24.03-LTS/everything/x86_64/ \
  --setopt=stage1-everything.gpgcheck=1 \
  --setopt=stage1-everything.gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-openEuler \
  install -y bpftool libbpf-devel pkgconf-pkg-config elfutils-libelf-devel zlib-devel
```

本机本次仅新安装 bpftool 和 libbpf-devel，未升级内核，未持久启用额外仓库。

## 四、Verifier 错误与修复实验

也可单独执行：

```bash
sudo make check-verifier
```

实验加载器只执行 open/load/close，不挂载、不 pin；每组都要求修复版确实加载成功。
权限拒绝、文件损坏或编译错误不会被当作预期的 Verifier 拒绝。

| 实验 | 错误原因 | 核心修复 |
|---|---|---|
| map_null | 未判空就解引用 map 查找返回值 | `if (!value) return 0;` 后再访问 |
| map_bounds | 8 字节 value 被当作两个 u64 使用 | 限定索引到 value 的真实边界 |
| ringbuf_release | reserve 后直接 return，引用未释放 | 每条路径都 submit 或 discard |

本机对应的关键拒绝行：

```text
R0 invalid mem access 'map_value_or_null'
invalid access to map value, value_size=8 off=8 size=8
Unreleased reference id=2 alloc_insn=4
```

完整日志还包含指令与寄存器状态，先找最后的明确拒绝行，再向前追查是哪次 helper
调用或哪次访存导致状态不合法。不要把日志里单纯出现的指针类型当作拒绝原因。
参考：[内核 Verifier 文档](https://docs.kernel.org/bpf/verifier.html)、
[ringbuf 引用跟踪说明](https://docs.kernel.org/bpf/ringbuf.html)。

若局部数组或调用链栈使用超过 512 字节，编译器也可能先拒绝生成 BPF 对象。
这类编译错误和内核 Verifier 拒绝应分别记录，不混为一次“内核拒绝实验”。

## 五、成员独立复现和讲解

每位成员分别完成下列步骤，再请另一位成员核验并填写记录：

1. 关闭教程和现有实现，独立复现或重写一个简化的 exec/ringbuf 探针与加载器。
   在个人分支、规定目录中开发；只提交审查通过的有效代码，实验失败代码保留在忽略目录。
2. 编译、加载探针，另开终端运行 `true`，确认进程身份、路径与 JSON 输出。
3. 运行 IO 示例与测试，解释 issue/complete 关联键、部分完成、重入队和累计快照。
4. 阅读一条自己遇到的 Verifier 日志，说明拒绝原因，修复后重新加载通过。
5. 运行工程验收命令并记录 commit、内核、证据目录、关键结果和自己的解释。

讲解至少覆盖：

- open/load/attach/poll/cleanup 各自做什么；编译成功为何仍可能无法 load。
- reserve/submit/discard 与 output 的区别，以及如何处理队列满。
- PID 与线程 ID 的区别、成功 exec 事件和 execve 调用尝试的区别。
- IO 完成上下文为何不能直接充当发起者身份；request 指针为何适合作为配对键。
- map 读取为何要判空并检查边界；为什么在线累计快照不保证跨 CPU 同时一致。
- JSON Lines 与人类提示为何分流；单调时钟为何不能直接当日历时间。

先由成员用自己的话回答，核验者再对照源码和实际输出提问。
