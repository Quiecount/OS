# 两个场景分别验收：当前结果与建议目标

更新：2026-11-19。以下“阶段目标”“优秀目标”都是 AI 根据现有实现提出的工程建议，不是赛方标准、行业统一门槛或官方评分。旧文档的 5% 同样为暂定建议，并非原始需求。本文给出今后可验证的目标，不代表已经实现。

目前有两个场景模块：syscall 热点，以及 CPU 占用/调度延迟。第二个模块含 CPU_HOG、SCHED_DELAY 两种诊断，所以两个模块对应三种现有告警。CPU 使用率通过 /proc 累计 CPU 时间差计算，调度指标由 eBPF 采集。

## 场景一：高频/高耗时 syscall 热点

现有观测：newfstatat 主要负载窗口约 21.69 万～23.36 万次/秒、平均延迟 3.68～3.89 μs、P99 桶上界 8 μs。这些是负载状态，并非工具质量的优秀线。

| 评价项 | 当前证据 | 下一阶段目标 | 建议优秀目标 |
|---|---|---|---|
| 调用计数误差 | 1/4/8 线程 getpid 各一次，误差 0% | 各测试组合 ≤0.5% | 各组合 ≤0.1%，持续至少 30 分钟 |
| 平均延迟测量误差 | 已输出，未独立校验 | ≤max(2 μs, 参考值的 15%) | ≤max(1 μs, 参考值的 10%) |
| P99 测量误差 | 2 的幂分桶，上界估计，未独立校验 | 输出所在区间与分辨率 | ≤max(1 μs, 参考 P99 的 20%)；需细化桶 |
| 热点告警时效 | 能检出，未做系统时效测试 | 稳定超阈值后 ≤3 秒 | 稳定超阈值后 ≤2 秒，汇总周期 1 秒 |
| 高耗时告警覆盖 | 已采延迟，缺独立慢调用告警 | 补低频慢调用规则 | 高频短调用、低频慢调用、混合负载均正确分类 |
| 检出率/误报率 | 最后一次注入检出，不能估算总体概率 | 建立固定正负测试集 | 检出率 ≥98%，正常样本误报率 ≤1% |
| syscall 压测吞吐损失 | 同轮原版 24.55%，优化版 13.92% | ≤10% | ≤5%，保持逐次采集与相同负载 |
| 加载器资源占用 | RSS 最大值 3.53 MiB | CPU ≤5% 单核、RSS ≤64 MiB | CPU ≤2% 单核、RSS ≤32 MiB；验证长时运行 |

测试组合：getpid、newfstatat、openat/close；1/4/8 线程；1/10/20 万次每秒三个负载档。无法达到指定负载时报告实际负载和容量限制。同一实验同时检查准确性与开销，不用不同模式的数据拼成“优秀”。

延迟参考应采用相同入口/出口语义的逐事件时间戳，在独立准确性实验中离线计算均值/P99，并说明参考采集自身的扰动。不能把另一轮运行的延迟或吞吐倒数当作测量真值。当前 8 μs 桶上界不能证明满足 20% 误差目标。

## 场景二：CPU 异常占用与调度延迟

现有观测：单线程压测 CPU 为 90.91%～92.97% 单核，首次 CPU_HOG 持续时间字段为 10.01 秒；拥堵时 runqlat P99 桶上界主要为 4.096～16.384 ms。最大进程窗口累计运行队列等待 532.387 ms。

| 评价项 | 当前证据 | 下一阶段目标 | 建议优秀目标 |
|---|---|---|---|
| CPU 使用率误差 | 已修复跨窗口尖峰，单线程 ≤105% 回归通过，未独立校验 | 对齐窗口误差 ≤5 个百分点 | 5 秒窗口误差 ≤2 个百分点；另验证 1 秒告警窗口 |
| CPU_HOG 时效 | 本次累计 10.01 秒时告警 | 真正连续 >80% 满 10 秒后 ≤2 秒告警 | 同左，且所有测试组合满足、短于 10 秒的突发不误报 |
| runqlat P99 误差 | 有直方图与桶上界，未独立校验 | 对照相同就绪→运行事件验证区间 | ≤max(5 μs, 参考 P99 的 20%)；需细化桶 |
| SCHED_DELAY 时效 | 拥堵注入检出，尚未系统测量时效 | 满足阈值及样本量后 ≤3 秒 | 满足条件后 ≤2 秒，至少 20 样本/窗口 |
| 完整 off-CPU | 仅运行队列等待，缺睡眠/I/O 阻塞总时长 | 补总时长，与 runqlat 分开输出 | 可控睡眠、阻塞、抢占用例中总时长误差 ≤5%，验证跨窗口统计 |
| 检出率/误报率 | 最后一次两种异常均检出 | 两种告警分别建立正负测试集 | 每种检出率 ≥98%、误报率 ≤1% |
| CPU 压测吞吐损失 | 三轮中位数 -0.77%，属于波动 | 稳定复测 ≤5% | 稳定复测 ≤2% |
| 加载器资源占用 | CPU 中位数 0.6% 单核，RSS 最大值 4 MiB | CPU ≤5% 单核、RSS ≤64 MiB | CPU ≤2% 单核、RSS ≤32 MiB；验证长时运行 |

CPU 误差用百分点：参考 90%、观测 92%，误差是 2 个百分点。采用独立线程 CPU 时钟/进程累计时间进行对齐窗口校验；仅与同样读取 /proc 的工具一致，不代表充分独立验证。

测试覆盖 20%/50%/75%/85%/100% 单核负载、5/9/10/15 秒持续时间、多线程总占用。四核 VM 调度测试使用 1/4/8/16 个 worker，加入睡眠与 I/O 阻塞检查分类。基线先在同环境正常负载下测量；原验收脚本的 100 μs 只是注入参数。

## 统一测试协议，分别报告结果

1. 每种告警至少 100 个独立异常试验、200 个独立正常试验，覆盖上述组合。目标对应每种至少 98/100 检出、最多 2/200 正常试验误报。预先规定期望 PID、异常类型、阈值和时效；重复告警窗口不能增加试验数。报告经验比例、样本数和置信区间，不保证真实业务中的同等成功率。旧“3/3”只代表一次验收中三类异常均命中。
2. 固定 VM 配置、负载和采集模式，至少 10 组交替开关对照，每组稳定负载至少 30 秒，另留预热时间。保存全部原始数据、中位数与离散程度。负数按噪声理解；基线明显漂移则整批标注环境不稳定并复测，不选择性删除不利样本。
3. 连续运行至少 30 分钟，检查准确性、CPU、RSS、异常退出、丢记录和容量饱和。RSS 不含内核 BPF map 内存，另行报告 map 容量及内存。
4. 分别报告两个模块的功能覆盖、准确性、识别质量、时效、开销，不再混成“2/4”总分。吞吐倒数推算的耗时增量与吞吐损失同源，不重复计分。对应模块全部目标都有测试证据，才可称达到这里建议的“优秀目标”。

## 依据与建议值的边界

- 本地《2026 华东区域赛技术方案》给出评分维度，未规定这两个模块的数值优秀线。
- 开发计划中的基线 ×10、CPU >80% 持续 10 秒、runqlat P99 >基线 ×5 是诊断规则，不是工具优秀指标。
- [Prometheus 官方直方图说明](https://prometheus.io/docs/practices/histograms/)说明分位数估计误差受桶宽影响，支持细化分桶的方法，不提供本文 20% 目标线。
- [BPF Performance Testing，bpfconf 2024](https://vger.kernel.org/bpfconf2024_material/BPF_Performance.pdf)讨论挂载、helper 与基准测试，不提供本项目统一的 5% 或 2% 优秀线。
- 表中的百分比、时间与资源目标均为建议值。调整目标应保留原标准和原因，不能为让现有结果达标而事后改线。
