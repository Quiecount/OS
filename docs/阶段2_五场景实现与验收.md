## 场景 3：IO 延迟、IOPS、观察到的在途深度

探针：`src/probes/io_latency.bpf.c`。加载器：`src/loader/stage2.c` 的 IO 分支，
构建为 `build/io_latency`。公共布局在 `src/common/stage2.h`，事件尾部按契约 v1.3 追加。

`tp_btf/block_rq_issue` 获取 request 指针，保存 issue 时间、进程/UID/comm、
leader start_boottime、设备 major/minor、操作与长度。只采 read/write、有数据的请求。
complete 可在中断/其他线程上下文发生，不能用完成时的 current 归因。
`block_rq_complete` 遇部分完成保留记录；最终完成才计时、输出并删除。
`block_rq_requeue` 删除旧计时并减在途计数，下一次 issue 重新计时。

用户态按进程实例、设备、操作聚合：完成次数/字节数、IOPS、平均、384 桶细分 P99、
错误次数、完成请求携带的 `queue_depth_observed_max`。
后者只是本探针跟踪的该设备已 issue 未完成请求数，若指定 `--pid` 则只涵盖该 PID；
不是硬件队列深度，也不含尚未下发的块层排队时间。IOPS 不含文件系统/page cache 命中。
同一逻辑 IO 在堆叠设备层可能被多次观测，不能把各设备的字节数直接相加当业务吞吐。
异步回写时只报告 issue 线程，不能恢复原始文件写入者或文件名。

`IO_JITTER`：同进程、设备、写操作完成样本至少 20；延迟严格超过
`--baseline-p99-us`（默认 1000μs）×5 的样本数 > floor(samples/100)。
输出 P99 是桶上界，判定用实际超阈值计数，避免桶上界造成边界误报。
`faults/03_io.sh` 用唯一临时普通文件、libaio、direct=1、64KiB、iodepth=32、64MiB 文件，
到时退出并清理，不写裸设备、不覆写固定路径。

## 场景 4：缺页、大块 mmap、RSS 与 OOM

探针：`src/probes/mem_pressure.bpf.c`，加载为 `build/mem_pressure`。

- `exceptions/page_fault_user` 按进程实例在 PERCPU_HASH 中累计用户态缺页数与最后地址，
  不逐缺页写 ringbuf。该异常包含不同类型缺页，不等同 major fault、磁盘交换或物理内存不足。
- mmap 进入统计≥1MiB的请求长度，进入/退出按 TID 关联，失败单独统计；
  字节数是请求的虚拟长度，包括失败请求，不当作已分配物理页。
- 每窗口读取累计 map 做差，不在 BPF 更新时反复删除统计记录。
  RSS 从绑定同一 `/proc/PID` 目录描述符的 stat/statm 获取，并核对进程开始时间；
  首次、退出等情况使用 valid 标志和 null，不编造 0 增速。
- `oom:mark_victim` 原始参数只给 victim PID。输出 `oom` 和 `OOM_KILL`，
  元数据未知时明确 `identity_known=false`；uid=0/空 comm 不能解释为 root 进程。
  该事件证明内核选出了 victim，不是验证它最终一定退出的进程死亡通知。
- `MEM_PRESSURE` 使用缺页率>配置基线×5作为排查线索；默认 `--baseline-faults 1000`。
  `faults/04_mem.sh` 默认一个 64MiB 工作集，反复触页，不以杀死全机进程作为注入方法。

OOM 回归只将专用测试子进程加入新建的 memory cgroup，memory 与 memory+swap 均限 32MiB，
让它触页 128MiB；加载器、测试父进程留在外部。断言被杀 PID 与事件一致，最后回收子进程并删除 cgroup。
不修改全局 OOM 参数或宿主机内存限制。

## 场景 5：同锁等待、并发数、用户等待栈

探针：`src/probes/lock_contention.bpf.c`，加载为 `build/lock_contention`。
故障程序改为 `build/lock_workload`，避免与加载器同名覆盖。

sys_enter/exit_futex 按 TID 配对，只采 WAIT、WAIT_BITSET（去除 private/clock flags）。
同锁按进程 leader 开始时间、TGID、用户地址关联；不同进程同值虚拟地址不会混合。
进入增加同锁 WAIT 调用数，完成携带进入时并发计数；EAGAIN 单独统计，不进入等待直方图。
timeout、interrupted、其他错误分列。进程退出回收未完成的线程状态。
完整进入→退出等待包括排队、睡眠和再次被调度，跨窗口归入退出窗口。

sched_switch 对正在 WAIT 的线程累计完整 off-CPU 区间，采集用户栈；
每个完成样本携带最后一次取得的用户 stack_id（无切出时用进入栈）。
用户态按同锁/操作聚合栈次数，最多保留 16 组栈和 16 个 TID，每栈最多 32 帧。
额外样本和取栈错误有独立计数。帧是 hex 地址，未做符号化，须结合相应进程映射/调试信息解释。

`LOCK_CONTENTION`：并发 WAIT 调用数≥`--min-waiters`（默认3）且完成等待总时长>
`--wait-ms`（默认100ms）。诊断的 key_metrics 附栈/TID，collector 汇总后仍保留。
WAIT 也用于条件变量、join 等正常同步；单凭该规则不能认定是 pthread mutex 故障。
尚未完成的无限等待不会进入完成时长统计；跨进程共享 futex、futex2、PI/requeue 跨锁关联不在本轮范围。

注入程序 8 线程抢一锁，临界区暂停 1ms；到时或收到信号后停止并 join，避免忙循环、counter 数据竞争和 timeout 掩盖错误。

## 容量、完整性与兼容性边界

IO 请求表32768、设备计数表1024；内存累计进程实例表4096、mmap关联16384；
锁等待16384、锁计数4096、栈4096；用户窗口聚合最多4096组。所有 map/内存有界。
锁计数的零值不删，避免删除与其他线程加减并发产生错误；内存退出进程记录保留以读到最后计数。
长时间运行累计达到容量后会报告 tracking_failures，需要重启采集器；后续可优化安全回收。

ringbuf 为256KiB；IO/锁高事件速率可能丢样。健康行报告累计 tracking_failures、
ringbuf_dropped、aggregation_dropped。**一旦看到任何采集失败，本轮运行后续窗口一律标为不完整并抑制阈值告警**；
OOM 已收到的直接证据仍输出。该保护不把容量不足变成假成功，也不意味着受损运行中先前窗口可追溯补齐。
统计快照并非全 map 原子快照，窗口边界允许短暂偏移。P99 纳秒输出是细分桶上界向上取整到微秒。

本轮仅实测上述 6.6/x86_64 环境；缺页 tracepoint 是 x86 特定接口，ARM64/5.10 的挂载参数和 CO-RE
均需单独适配验证。尚未完成10分钟正常态基线、统一 osmedic CLI、LLM 和五场景完整开销评测，
这些继续按开发计划阶段3及以后推进。
