# 场景 1–2：实现、阈值与性能评测

## 功能与数据口径

`syscall_hotspot` 挂载 `raw_tp/sys_enter` 和 `raw_tp/sys_exit`。内核用 TID 关联进入和退出，按进程 PID + syscall ID 聚合完成次数、耗时总和与 26 桶延迟直方图；用户态每秒输出 Top-N 的频率、平均延迟与 P99 桶上界。默认规则是频率至少 1000 次/秒、超过配置基线（默认 1000 次/秒）的 10 倍、且进入 Top-N，输出 `SYSCALL_HOTSPOT`。`--baseline-rate`、`--min-rate`、`--top` 可调整。默认基线仅为演示起点；正式比较需要在同一机器、同一负载下先采正常态基线，再输入 `--baseline-rate`。

`cpu_hog` 挂载 `raw_tp/sched_switch`、`raw_tp/sched_wakeup` 和 `raw_tp/sched_wakeup_new`。eBPF 按线程记录调度事件并按进程聚合等待直方图；加载器通过 /proc/PID/stat 的 utime + stime 窗口差值计算 CPU 使用率，避免长时间不切换的线程将多秒运行时间集中记入一个窗口。`cpu_percent_one_core` 以一个 CPU 核的容量为 100%，多线程进程可以大于 100%。连续超过 80% 达 10 秒时输出 `CPU_HOG`。全局 runqlat P99 桶上界超过配置基线（默认 1000 µs）的 5 倍、窗口至少 20 次样本时输出 `SCHED_DELAY`。`--baseline-p99-us` 可调整。

P99 是 2 的幂直方图**桶上界估计**，并非精确百分位。`runq_wait_ms` 统计就绪队列等待，不包含主动睡眠、磁盘 I/O 阻塞；这比把所有 off-CPU 时间当调度延迟更准确。两支探针均排除加载器本身的 PID。当前版本是整机观测，不区分容器，也没有保存跨运行的自学习基线。

高频场景在内核 map 中聚合，加载器输出窗口 JSONL，而非把每次 syscall/调度事件逐条塞进 ring buffer。JSONL 包含接口契约的 `scene`、`ts_ns`、`pid`、`uid`、`comm` 公共字段，并以 `event` 区分 `*_metric` 与 `diagnosis`。两场景规则目前由加载器判定，`analysis/collector.py` 将诊断行汇总为七字段报告；`confidence=1.0` 表示规则条件确实命中，不是根因概率的统计校准值。

## 复现与验收

```bash
make check
sudo bash tests/stage2-two-scenarios.sh
```

脚本编译 `faults/syscall_bomb.c`，调用 `fstatat` 制造系统调用热点；用 `stress-ng --cpu 1` 制造持续 CPU 占用，再用 `stress-ng --cpu 8` 在四核 VM 制造调度拥堵。验收检查 JSON 解析、`SYSCALL_HOTSPOT`、`CPU_HOG`、`SCHED_DELAY`、调度指标和诊断必需字段，成功时输出 `STAGE2_TWO_SCENARIOS_OK`。拥堵测试把 P99 基线设为 100 µs，便于在目标 VM 稳定复现，不能当作实际正常态基线。

## 性能指标与“优秀”目标

本地《2026 华东区域赛技术方案》第 3 页给出应用开发赛道参考权重：代码 30%、文档 30%、教学价值 10%、规范 10%、演示答辩 20%；**没有给出 CPU、内存、时延或吞吐的“优秀”数值线，也没有规定可由开发者自行计算的官方分数**。项目开发计划中的 40/30/15/15 是内部策略，不能称为官方评分。

为便于迭代，本项目暂用下列**自定工程目标**；这些数值不是赛方标准：

| 指标 | 当前工程目标 | 测量方式 |
|---|---:|---|
| 探针引起的 syscall 与 CPU 负载吞吐下降 | ≤5% | 同机同负载，开关探针配对 3 次，比较吞吐中位数 |
| 由吞吐倒数推算的每操作平均耗时增加 | ≤5.3% | `baseline_rate / monitored_rate - 1`；仅是等效均值，不是 P99 |
| 加载器进程 CPU（用户态 + 内核态） | ≤5% 单核 | `/proc/PID/stat` 的 utime + stime，采样期间时钟滴答 |
| 加载器 RSS | ≤64 MiB | `/proc/PID/status`，采样最大值 |
| 两场景三个异常注入识别 | 3/3 | `tests/stage2-two-scenarios.sh` |

定值 5% 是项目组的低干扰目标。`bench-two-scenarios.py` 输出原始每轮数据及中位数到 `output/benchmark/result.json`。主机调度、虚拟机竞争、负载持续时间会影响结果；比较需要相同 VM 配置、同一时段、交替运行开关组。`stress-ng` 的 bogo ops 是其自身吞吐单位，不能跨版本或跨机器直接比较。加载器进程 CPU 不等于内核 BPF CPU；吞吐差异才包含内核探针影响。

```bash
sudo python3 tests/bench-two-scenarios.py
# 快速单轮检查（不能用作最终性能结论）
sudo env TRIALS=1 python3 tests/bench-two-scenarios.py

# 只复测 syscall；结果写入 output/benchmark/result-syscall.json
sudo env SCENARIOS=syscall python3 tests/bench-two-scenarios.py
```

### 当前验收记录（2026-11-19）

- openEuler 24.03 LTS，内核 `6.6.0-145.0.13.139.oe2403.x86_64`：合入最新 `main` 框架后，`make check` 编译 7 支 BPF 对象、3 个加载器和 2 个注入程序，成功；无编译警告。`analysis/collector.py` 将场景诊断行转为仓库约定的七字段报告。
- 在 openEuler VM 中以 sudo 执行 `tests/stage2-two-scenarios.sh`，三项注入识别 **3/3**：`SYSCALL_HOTSPOT` 命中 5 个窗口，`CPU_HOG` 命中 2 个窗口，`SCHED_DELAY` 命中 6 个窗口；对应峰值为 400191.18 次/秒、单核 95.96% CPU、runqlat P99 桶上界 8.192 ms。三份七字段报告均由 collector 生成并通过脚本断言。
- 原版探针的 3 轮开关对照结果如下。每行分别取关、开探针时的吞吐中位数；等效平均耗时增加由吞吐倒数推算，**没有实测 P99 耗时增量**。

| 压测 | 关闭探针吞吐 | 开启探针吞吐 | 吞吐下降 | 等效平均耗时增加 | 加载器 CPU 中位数 | 加载器 RSS 最大值 |
|---|---:|---:|---:|---:|---:|---:|
| `syscall_bomb` | 523101 次/秒 | 410223 次/秒 | **21.58%** | 27.52% | 0% 单核 | 3.54 MiB |
| `stress-ng --cpu 1` | 1772.69 bogo ops/秒 | 1759.50 bogo ops/秒 | **0.74%** | 0.75% | 0% 单核 | 3.78 MiB |

- **当前项目内部验收：**3/3 异常识别、3/3 加载器编译、2/2 collector 契约测试通过；四类性能目标中 2/4 达标（加载器 CPU、RSS），吞吐下降和等效平均耗时两类目标因 syscall 场景未达标。`stress-ng` 开探针的一轮仅 1147.28 bogo ops/秒，表明 VM 抖动明显；CPU 场景的 0.74% 中位数结论仍需在稳定宿主机扩大样本验证。**这些是项目内部验收数字，不是赛事官方分数。**
- 优化对照：将 syscall 起始时间表改为普通 HASH，3 轮配对吞吐下降 27.58%；改用 PERCPU_HASH 聚合，下降 21.77%；task storage 尝试在注入验收中检出 3/3，但热点调用速率明显下降。均未优于原版，因此当时保留原版；后续的线程记录复用优化见下节。各轮宿主机负载不同，基线中位数从约 523k 降到约 229k 次/秒；只能在每轮开关配对内比较比例，不能跨轮直接比较绝对吞吐。原始测量结果保存在本地 `output/benchmark/`，该目录不入库。

### 线程计时记录复用优化（2026-11-19）

原版在每次 syscall 进入时更新 LRU 表、退出时删除记录。优化后同一线程复用记录，在退出时将计时起点置零，在线程结束的 `sched_process_exit` 清理记录。LRU 容量仍为 65536，保留有界内存；若容量压力导致尚未退出的记录被淘汰，仍可能漏计，与原版相同。此优化不引入采样，仍逐次统计调用数和延迟。

同一时段交替运行关闭探针、原版、优化版，各 6 次；吞吐中位数分别为 273221.5、208862.5、229653.5 次/秒。原版损失 **23.56%**，记录复用版 **15.95%**，相对原版吞吐增加约 **9.95%**。该结果优于原版，但尚未达到 ≤5% 的工程目标。1、4、8 线程分别发起 20001、80001、160001 次 getpid，采集计数全部一致；三类异常注入识别仍通过。

第二轮将 248 字节统计结构的清零移入首次创建记录的分支，反汇编确认热点路径省去 31 次清零写入。最终 6 轮同环境对照：关闭探针 272324.5 次/秒、原版 205477.5 次/秒、最终优化版 234406.5 次/秒；吞吐损失 **24.55% → 13.92%**，优化版相对原版吞吐增加 **14.08%**。等效平均耗时增加 16.18%，仍未达到 ≤5.3% 目标。该轮同时包含记录复用与清零优化，不能把全部收益单独归因于清零优化。

第二轮完整验收曾发现 CPU_HOG 漏报：单线程长期不发生 sched_switch 时，旧版在切出时一次性累计运行时间，实测出现 224%–350% 的单窗口尖峰，中间空窗口打断持续时间判定。已将 CPU 使用率来源改为 `/proc/PID/stat` 的累计 CPU 时间差，按 PID + 进程启动时间识别进程重用。eBPF 继续提供 runqlat 直方图和调度等待。累计时间的分辨率为 `1 / CLK_TCK` 秒，窗口边界存在量化误差；两个采样之间创建又退出的短进程可能缺失 CPU 样本，已经退出进程的最后一段 CPU 时间也可能漏计。因此此 CPU_HOG 规则面向持续存在的高占用进程。旧版 CPU 开销数据不代表修复版，需重新测量。

修复版完整复测入口为 `sudo python3 tests/validate-two-scenario-optimization.py`，分别记录三项检查的退出码、源码 SHA256 和开始时间。新增单线程窗口 CPU 不超过 105% 的断言。各项检查相互独立，失败日志保存在 `output/optimization-validation/`。

最终验证（2026-11-19 13:36 开始，北京时间）：三项检查均返回 0。异常检出窗口为 SYSCALL_HOTSPOT=4、CPU_HOG=3、SCHED_DELAY=7；1/4/8 线程计数检查误差均为 0%，单线程 CPU 尖峰回归检查通过。修复版 CPU 负载三轮对照中位数为关闭 920.36、开启 927.49 bogo ops/秒，损失 -0.77%；负数应按 VM 测试波动理解，不能宣称监控加速业务。加载器 CPU 中位数 0.6% 单核，RSS 最大值 4.00 MiB；syscall 加载器 RSS 最大值 3.53 MiB。四类性能目标仍为 **2/4 达标**：CPU 和 RSS 通过，吞吐与等效平均耗时因 syscall 场景未达标；功能识别 **3/3**。这是内部验收状态，不是赛事得分。

复现对照前，先从原版源码构建并保存 `build/syscall_hotspot-before`，再构建优化版；脚本不会自动生成原版二进制：

```bash
sudo bash tests/stage2-two-scenarios.sh
sudo python3 tests/compare-syscall-performance.py
```

对照脚本先验证 1、4、8 线程计数误差不超过 0.5%，再轮换三组执行顺序，保留每轮原始数据和中位数到 `output/syscall-optimization/result.json`。单次调用的延迟仍是直方图桶上界估计，计数准确不代表 P99 估计误差为零。
