## 一、总体架构：五层流水线的落地

```
┌─ 内核态 ──────────────────────────────────────────────┐
│  探针（src/probes/*.bpf.c，每场景一个）                 │
│    execsnoop ✅  syscall_hotspot  cpu_hog              │
│    io_latency  mem_pressure  lock_contention（骨架）   │
└──────────────┬────────────────────────────────────────┘
               │ ringbuf（events map）
┌──────────────▼────────────────────────────────────────┐
│ 加载器（src/loader/*.c，每场景一个，阶段 2 逐个补齐）    │
│   职责：装探针 → 收事件 → 打印 JSON Lines              │
└──────────────┬────────────────────────────────────────┘
               │ JSON Lines（事件契约见 §三）
┌──────────────▼────────────────────────────────────────┐
│ 聚合与规则引擎（analysis/collector.py，阶段 3）          │
│   读取 → 按场景聚合指标 → 基线对比 → 命中规则           │
└──────────────┬────────────────────────────────────────┘
               │ 七字段诊断 JSON（契约=开发计划 §四）
┌──────────────▼────────────────────────────────────────┐
│ LLM 报告层（report/，阶段 4）→ 人类可读诊断报告          │
└───────────────────────────────────────────────────────┘

配套：faults/ 五场景注入（复现异常）· tests/test.sh（一键回归）· deploy.sh（评委入口）
```

## 三、事件契约（src/events.h）

- 所有场景事件以 **`struct ev_common`** 开头（`ts_ns / pid / uid / comm`）——analysis 层统一按此解析
- 每场景一个 `ev_<场景>` 结构，场景特有字段跟在公共头后面
- 加载器把事件打印为 **JSON Lines**，每行至少含：`{"scene":"...","ts_ns":...,"pid":...,"uid":...,"comm":"..."}`
- **加字段不改字段**：后续阶段只允许在结构体尾部追加字段（ringbuf 消费端按场景结构解析，中部插入会破坏兼容）

## 四、五场景实现要点（骨架 → 填肉清单）

| 场景 | 探针文件 | 挂载点（骨架已挂） | 阶段 2 要补的肉 |
|---|---|---|---|
| 1 syscall 热点 | `syscall_hotspot.bpf.c` | `raw_syscalls/sys_enter` | 改 hash map 聚合（key={pid,id}）；补 `sys_exit` 配对算单次延迟 |
| 2 CPU/调度 | `cpu_hog.bpf.c` | `sched/sched_switch` | `sched_wakeup` 配对算 runqlat；每进程 CPU% 与 off-cpu 时长 |
| 3 IO 延迟 | `io_latency.bpf.c` | `block/block_rq_issue` | 补 `block_rq_complete`，hash map 配对计时；按进程/设备出分位数 |
| 4 内存/OOM | `mem_pressure.bpf.c` | `exceptions/page_fault_user` | 缺页速率窗口统计；`sys_enter_mmap` 大块申请；`oom/oom_mark_victim` |
| 5 锁竞争 | `lock_contention.bpf.c` | `syscalls/sys_enter_futex` | `sys_exit_futex` 配对计时；等待栈聚合定位"哪把锁谁在排队" |

> 动工每个场景前，先在目标内核实测挂载点名：`bpftrace -l 'tracepoint:块:*'`（名字随内核版本有差异）。

## 五、如何完善一个场景（标准三步，以场景 3 为例）

1. **填探针**：改 `src/probes/io_latency.bpf.c`——按 §四 的清单补 map 与字段（`events.h` 里追加场景字段）
2. **配加载器**：复制 `src/loader/execsnoop.c` 为 `io_latency.c`，改三处（目标 .o 文件名、程序名、事件结构），Makefile 加两个目标
3. **验证闭环**：`make` → `sudo ./build/io_latency > /tmp/io.jsonl` → 另开终端 `./faults/03_io.sh` → `python3 analysis/collector.py --input /tmp/io.jsonl` 看到事件计数

三步走完即满足开发计划对该场景的"完成定义"（可注入、可复现、有输出）。

## 六、构建与运行

